# Austin 消息推送平台 - 简历与面试冲刺宝典

## 一、项目描述 (Project Descriptions)

### 1. 简历书写版 (STAR 法则)

- **构建三层背压防护体系**：设计生产端 Semaphore 限流 + 消费端 AIMD 自适应水位 + 下游令牌桶三级防护，通过 Redis Pub/Sub 实现上下游协同，系统饱和时 429 快速失败，雪崩风险降低 40%
- **实现配置中心动态管控**：接入 Nacos 配置中心，限流阈值、去重窗口、盾牌时段等参数支持秒级热更新，无需重启即可响应业务变化，运维效率提升 60%
- **设计全链路可观测体系**：集成 Elasticsearch 追踪 (TraceInfo) + Loki 结构化日志 (JSON + MDC) + Prometheus 指标 (消费延迟/背压状态/信号量水位)，问题定位时间从小时级缩短至分钟级，排查效率提升 80%
- **优化大数据量调度任务**：通过 XXL-JOB 分片广播 + CSV 流式读取 + 懒加载批处理，支撑百万级人群包定时触达，内存占用降低 95% (从 O(n) 降至 O(1))

### 2. 详细描述版

**项目背景**：企业内部统一消息推送平台，解决各业务线重复对接短信/邮件/IM 服务商、发送状态不可追踪、夜间骚扰用户等痛点。

**技术架构**：
- **后端核心**：Java 21 + Spring Boot 2.5.6 + Maven 多模块 (austin-web/handler/service/cron/stream)
- **消息队列**：Kafka (分 6-12 partitions/groupId 动态注册 Receiver)
- **存储层**：MySQL 5.7+ (业务配置) + Redis (去重/缓存/pub-sub) + Elasticsearch (追踪查询)
- **配置中心**：Nacos (限流/去重参数动态热更新)
- **调度系统**：XXL-JOB (CONSISTENT_HASH 分片策略)
- **可观测性**：Prometheus + Grafana (指标) + Loki (日志) + ES (分布式追踪)

## 二、核心项目亮点池 (Project Highlights Pool)

### 1. Chain of Responsibility 责任链模式治理消息流程
使用 `BusinessProcess` 接口统一 5 个处理环节 (丢弃/盾牌/去重/敏感词/发送)，`ProcessController` 顺序执行，任一环节调用 `context.setNeedBreak(true)` 立即中断。相比 if-else 嵌套，新增验证逻辑只需实现新 Action 类，符合开闭原则。

### 2. 三层背压防护体系 (生产端 + 消费端 + 下游端)
**第一层**：API 端 `MqRateLimiter` (Semaphore permits 从 Nacos 动态获取)，`tryAcquire` 快速失败返回 429，同时监听 Redis Pub/Sub 接收下游压力通知自动暂停发送。
**第二层**：消费端 `VirtualThreadBackPressureManager` + AIMD 自适应算法，根据每次消息下发耗时动态调整各渠道高/低水位，超过高水位暂停 Kafka 消费并通过 Redis Pub/Sub 通知上游生产者。
**第三层**：下游网关调用 `TokenBucketRateLimiter` 令牌桶限流，按渠道独立配置 QPS + burst，虚拟线程 sleep 等待令牌避免阻塞平台线程。

### 3. Nacos 配置中心动态管控
限流阈值 (Semaphore permits)、去重窗口/阈值、背压水位、盾牌时段等关键参数存储于 Nacos，支持秒级热更新无需重启。相比硬编码配置，可快速响应业务变化 (如大促期间临时提高限流阈值)，运维效率提升 60%。配合 `@NacosConfigListener` 实现配置变更实时推送。

### 4. Elasticsearch 查询策略优化
`EsDataController` 提供两套查询：`/es/trace/receiver` 按接收者查询 (使用 collapse by messageId + sort by timestamp 获取每个消息最新状态)，`/es/trace/traceId` 按追踪 ID 查询 (term 查询 + time-range 拉取全量记录)。索引设计采用时间滚动策略，单索引控制在 5000 万文档内。

### 5. Loki 高基数基数防护
`logback-spring.xml` 配置 LogstashEncoder 输出 JSON，MDC 字段严格限制为 `traceId`/`messageId`/`templateId`/`kafkaGroupId` 四类，禁止将 userId、手机号等高基数字段放入 MDC。日志文件 `logs/austin-app.log` 通过 Promtail 采集至 Loki，Label 仅用 `app`/`level` 两维度。

### 6. 全局异常治理与统一响应
`ExceptionHandlerAdvice` 统一捕获：`MessageTimeoutException` → 408、`SystemBusyException` → 429、`CommonException` → 500，所有响应包裹 `BasicResultVO.success()/fail()`。`MdcEnrichFilter` 在 HTTP 入口生成 traceId 注入 MDC，确保全链路可追踪。

### 7. Prometheus 指标暴露与告警
自定义指标包括：`austin.kafka.consumer.lag` (Gauge 消费延迟)、`austin.mq.semaphore.permits` (Gauge 剩余 permits)、`austin.backpressure.in_flight` (Gauge 飞行中消息数)、`austin.kafka.message.consumed` (Counter 成功/失败计数)、`austin.api.request.*` (HTTP 请求指标)。Grafana 配置背压触发告警 (in_flight > 400 持续 1 分钟)。

### 8. XXL-JOB 分片调度与流式 CSV 读取
`CronTaskHandler` 处理定时人群包任务，使用 `ReadFileUtils.getCsvRow()` 流式读取 (非 `getCsvRowList()` 全量加载)，配合 `CrowdBatchTaskPending` 懒加载批处理 (攒够 100 条发送一次)。XXL-JOB 配置 CONSISTENT_HASH 分片策略，确保同一任务始终路由到固定实例。

### 9. Redis + Caffeine 双层缓存
消息模板缓存：Caffeine LocalCache (5000 容量/10min TTL) + Redis 分布式缓存 (兜底)；渠道账号缓存：Caffeine (1000 容量/10min TTL)。去重计数器：`SimpleLimitService` (Redis String 每日零点过期) + `SlideWindowLimitService` (Redis ZSET + Lua 滑动窗口，精确到秒级)。

### 10. 滑动窗口去重 Lua 脚本
`SlideWindowLimitService` 使用 Redis ZSET 实现滑动窗口：key 为 `dedup:slice:{templateId}:{receiver}`，value 为 timestamp，score 为时间戳。Lua 脚本原子执行：移除窗口外元素 → 统计窗口内数量 → 超过阈值拒绝插入。相比固定时间窗口，避免临界点突发流量穿透。

### 11. Kafka 动态消费者注册
基于 `@Bean` 动态创建 `KafkaListenerContainerFactory`，每个 groupId/topic 组合独立一个 Receiver Bean。`MdcInterceptor` 从 Kafka Header 提取 traceId/messageId 注入 MDC，解决消费者线程上下文丢失问题。auto-commit=true (备注风险：可能重复消费)。

### 12. TraceUtils 异步追踪埋点
在Handler关键节点调用 `TraceUtils.sendTrace(traceId, messageId, ...)`，构建 `TraceInfo` 对象发送至 Kafka `trace-topic`。`TraceConsumer` 批量消费 (每 100 条或 5 秒刷写) 索引至 ES，避免同步写入影响主流程性能。

### 13. MDC 跨线程传播机制
`MdcUtil.wrap(Runnable)` 捕获当前线程 MDC 快照，返回的 Runnable 在执行时先恢复 MDC 再执行原逻辑。虚拟线程场景下，`ConsumeServiceImpl` 使用 `MdcUtil.wrap()` 包装消息处理逻辑，确保 `log.info()` 能打印正确的 traceId/messageId。

### 14. 消息模板热更新
`MessageTemplateCaching` 监听 Redis Pub/Sub 频道，收到模板变更通知后清除 Caffeine 缓存，下次查询从 Redis/MySQL 重新加载。相比定时全量刷新，减少 90% 无效 DB 查询。

### 15. 夜间盾牌策略免打扰
`ShieldAction` 读取渠道配置中的 `shieldStartTime`/`shieldEndTime`，当前时间落在盾牌时段内直接 `setNeedBreak(true)` 中断，记录盾牌日志。支持按渠道独立配置 (短信 22:00-8:00，邮件无盾牌)。

### 2. "三板斧"排查指南 (Loki + ES 联动)

#### 场景：用户反馈"昨晚 8 点的短信没收到"

---

**第一步：ES 定位消息轨迹**

使用 `EsDataController` 提供的接口：

```bash
# 方案 A：已知接收者手机号，查该用户所有消息记录
GET /es/trace/receiver?receiver=138xxxx1234&startTime=2024-03-29T20:00:00Z&endTime=2024-03-29T21:00:00Z

# 方案 B：已知 traceId (从业务系统日志获取)，查全链路记录
GET /es/trace/traceId?traceId=a1b2c3d4-xxxx-5678

# ES 内部查询逻辑：
# • receiver 查询：term + time-range + collapse by messageId (最新 per message)
# • traceId 查询：term + time-range (返回所有记录)
```

**ES 返回示例**：
```json
{
  "hits": [{
    "traceId": "a1b2c3d4-xxxx-5678",
    "messageId": "msg_001",
    "receiver": "138xxxx1234",
    "templateId": 1001,
    "status": "SEND_FAILED",
    "timestamp": "2024-03-29T20:05:32Z",
    "failReason": "Semaphore acquire timeout"
  }]
}
```

→ **初步结论**：消息在发送前被限流拦截。

---

**第二步：Loki 日志深钻失败原因**

使用 Grafana Explore 或 LogCLI 查询：

```logql
# 查询该 traceId 的所有 JSON 日志
{app="austin"} |= "traceId=a1b2c3d4-xxxx-5678"
| json
| line_format "{{.timestamp}} [{{.level}}] {{.message}}"
```

**日志输出示例**：
```
2024-03-29T20:05:31.234 [INFO]  Received message, traceId=a1b2c3d4, messageId=msg_001, templateId=1001
2024-03-29T20:05:31.456 [INFO]  Passing ShieldAction, currentHour=20
2024-03-29T20:05:31.567 [INFO]  Passing DeduplicationAction, dailyCount=5
2024-03-29T20:05:31.789 [WARN]  MqRateLimiter acquire failed, permits=0, traceId=a1b2c3d4
2024-03-29T20:05:31.890 [ERROR] SystemBusyException thrown, returning 429, traceId=a1b2c3d4
```

→ **精确结论**：20:05:31.789 时刻 Semaphore permits 耗尽，系统触发限流。

---

**第三步：Prometheus 指标确认系统状态**

Grafana Dashboard 查看关键指标面板：

```promql
# 查看当时信号量状态
austin.mq.semaphore.permits

# 查看背压状态
austin.backpressure.in_flight
austin.backpressure.paused

# 查看 Kafka 消费延迟
austin.kafka.consumer.lag{groupId="austin-consumer-group"}

# 查看该时间段 API 请求量
rate(austin.api.request.total[5m])
```

**指标快照 (20:05 时刻)**：
- `austin.mq.semaphore.permits` = 0 (耗尽)
- `austin.backpressure.in_flight` = 520 (超过 high=500)
- `austin.backpressure.paused` = 1 (消费者已暂停)
- `austin.kafka.consumer.lag` = 1500 (堆积 1500 条未消费)

→ **根因分析**：20:00-20:10 期间突发流量导致 in-flight 超过 500 高水位，触发背压暂停消费者，Semaphore permits 耗尽，后续消息被 429 拦截。

---

**排查总结**：
1. **ES** 快速定位到具体消息和失败状态
2. **Loki** 精确定位到失败环节和错误原因
3. **Prometheus** 确认系统当时的负载状态

传统方式需要 SSH 登录服务器 grep 日志，耗时 1-2 小时。使用三板斧流程，5 分钟内完成根因定位。

## 四、项目难点与解决方案 (Difficulties & Solutions)

### 难点 1：Kafka 消费积压 vs 下游网关限流的矛盾

**问题描述**：
- Kafka 消息堆积需要快速消费，但短信/邮件服务商 QPS 有限 (如短信 1000 QPS)
- 盲目加速消费导致下游拒绝，消息 retry 堆积，形成恶性循环
- 传统方案：线程池队列 + reject policy，但无法感知下游状态，且上下游隔离缺乏协同

**解决方案：三层背压防护 + AIMD 自适应算法**

```java
// 【第一层】API 端 Semaphore 限流 + Redis Pub/Sub 协同
@Component
public class MqRateLimiter {
    private Semaphore semaphore; // permits 从 Nacos 动态获取
    
    @NacosConfigListener(dataId = "rate-limit-config")
    public void onConfigChange(String config) {
        int newPermits = parsePermits(config);
        this.semaphore = new Semaphore(newPermits); // 热更新
    }
    
    public boolean tryAcquire() {
        if (isPausedFromRedis()) return false; // 监听下游压力
        return semaphore.tryAcquire();
    }
}

// 【第二层】消费端 AIMD 自适应背压控制器
@Component
public class VirtualThreadBackPressureManager {
    private final RtSensor rtSensor = new RtSensor(); // RT 传感器
    private volatile int highWatermark = 500;
    private volatile int lowWatermark = 200;
    
    // AIMD 算法：根据 RT 动态调整水位
    @Scheduled(fixedRate = 5000)
    public void adjustWatermark() {
        double avgRt = rtSensor.getAverageRt();
        if (avgRt > DANGER_THRESHOLD) {
            // RT 过高 → 乘法减小 (快速降低并发)
            highWatermark = (int) (highWatermark * 0.8);
            lowWatermark = (int) (lowWatermark * 0.8);
        } else if (avgRt < HEALTHY_THRESHOLD) {
            // RT 健康 → 加法增大 (缓慢提升并发)
            highWatermark += 10;
            lowWatermark += 10;
        }
    }
    
    public void beforeProcess(String groupId) {
        int count = inFlight.incrementAndGet();
        if (count >= highWatermark) {
            pauseKafkaContainers(groupId);
            publishToRedis(groupId, "pause"); // 通知上游暂停
        }
    }
}

// 【第三层】下游网关令牌桶限流
@Component
public class TokenBucketRateLimiter {
    private final int qps;      // 从 Nacos 获取
    private final int burst;
    
    public long acquire() {
        long waitMs = tokenBucket.acquire(); // 虚拟线程可安全 sleep
        return waitMs;
    }
}
```

**三层协同流程**：
1. **下游压力大** → 第三层令牌桶耗尽 → 等待时间变长 → 第二层 RT 上升
2. **第二层 RT 超阈值** → AIMD 降低水位 → 暂停消费 → Redis Pub/Sub 通知上游
3. **第一层收到通知** → 暂停发送 → 429 快速失败 → 保护整个系统

**效果**：
- 单机 QPS 稳定在 2000-5000，不压垮下游
- AIMD 自适应调整，无需人工干预
- 三层协同，雪崩风险降低 40%
- Nacos 热更新，大促期间无需重启

### 难点 2：异步线程上下文丢失 & 异常被吞掉

**问题描述**：
- 虚拟线程/线程池场景下，MDC 无法自动传递，日志缺少 traceId
- `CompletableFuture.runAsync()` 吞掉异常，主流程不知情
- Kafka 消费者异常未统一处理，消息静默失败

**解决方案：MDC 传播 + 全局异常捕获**

```java
// MdcUtil：MDC 跨线程传播
public class MdcUtil {
    public static Runnable wrap(Runnable runnable) {
        Map<String, String> mdcSnapshot = MDC.getCopyOfContextMap();
        return () -> {
            if (mdcSnapshot != null) {
                MDC.setContextMap(mdcSnapshot); // 恢复 MDC
            }
            try {
                runnable.run();
            } finally {
                MDC.clear(); // 清理，防止线程复用污染
            }
        };
    }
}

// ConsumeServiceImpl：虚拟线程中使用
@KafkaListener
public void consume(Message message) {
    executor.submit(MdcUtil.wrap(() -> {
        // 此处 log.info() 能打印正确的 traceId/messageId
        processMessage(message);
    }));
}

// ExceptionHandlerAdvice：全局异常统一处理
@RestControllerAdvice
public class ExceptionHandlerAdvice {
    @ExceptionHandler(MessageTimeoutException.class)
    public BasicResultVO handleTimeout(MessageTimeoutException e) {
        return BasicResultVO.fail(408, "Downstream timeout");
    }
    
    @ExceptionHandler(SystemBusyException.class)
    public BasicResultVO handleBusy(SystemBusyException e) {
        return BasicResultVO.fail(429, "System busy, try later");
    }
    
    @ExceptionHandler(CommonException.class)
    public BasicResultVO handleCommon(CommonException e) {
        return BasicResultVO.fail(500, e.getMessage());
    }
}
```

**效果**：
- 所有日志 (包括虚拟线程) 都包含完整 MDC 字段
- 异常统一返回标准化错误码，前端可区分"超时"vs"限流"vs"业务错误"
- Loki 可按 `level=ERROR` + `exceptionClass` 聚合告警

### 难点 3：MySQL 轨迹表慢查询 → 迁移 Elasticsearch

**问题描述**：
- 早期设计：消息轨迹写入 MySQL `message_trace` 表
- 问题 1：数据量达百万级后，`ORDER BY timestamp DESC` 查询超时 (5s+)
- 问题 2：按 receiver 聚合查询 (查某用户所有消息) 需要 filesort，索引失效
- 问题 3：无法支持"每条消息最新状态 collapse"语义

**解决方案：迁移 Elasticsearch，设计双查询策略**

```java
// EsDataController：两套查询接口
@RestController
@RequestMapping("/es/trace")
public class EsDataController {
    
    // 场景 1：查某接收者的所有消息 (最新 per message)
    @GetMapping("/receiver")
    public List<TraceInfo> queryByReceiver(String receiver, long start, long end) {
        // ES 查询：
        // 1. term query: receiver = "138xxxx"
        // 2. range query: timestamp in [start, end]
        // 3. collapse: field = "messageId" (每条消息只返回最新)
        // 4. sort: timestamp desc
        return esClient.search(...);
    }
    
    // 场景 2：查某 traceId 的全链路记录 (所有环节)
    @GetMapping("/traceId")
    public List<TraceInfo> queryByTraceId(String traceId, long start, long end) {
        // ES 查询：
        // 1. term query: traceId = "a1b2c3d4"
        // 2. range query: timestamp in [start, end]
        // 3. sort: timestamp asc (按时间顺序展示全流程)
        return esClient.search(...);
    }
}
```

**ES 索引设计**：
```json
{
  "mappings": {
    "properties": {
      "traceId": { "type": "keyword" },
      "messageId": { "type": "keyword" },
      "receiver": { "type": "keyword" },
      "templateId": { "type": "integer" },
      "status": { "type": "keyword" },
      "timestamp": { "type": "date" },
      "failReason": { "type": "text" }
    }
  },
  "settings": {
    "number_of_shards": 3,
    "number_of_replicas": 1,
    "index.lifecycle.name": "trace-rollover", // ILM 滚动策略

  }
}
```

**效果对比**：
| 维度 | MySQL | ES |
|------|-------|----|
| P99 查询延迟 | 5000ms+ | 50ms |
| 索引大小 | 10GB | 5GB (压缩) |
| collapse 支持 | ❌ (需应用层去重) | ✅ (原生支持) |
| 时间范围聚合 | ❌ (慢) | ✅ (fast aggregation) |

**😈 面试官提问 1**：你的责任链模式具体怎么实现的？如果某个环节需要异步执行怎么办？

**🎓 候选人解答**：
我定义了 `BusinessProcess` 接口，只有一个 `process(MessageContext context)` 方法。五个实现类分别是 `DiscardAction`、`ShieldAction`、`DeduplicationAction`、`SensWordsAction`、`SendMessageAction`。

`ProcessController` 里维护一个 `List<BusinessProcess>`，顺序遍历执行。每个 Action 执行完后检查 `context.isNeedBreak()`，如果为 true 就中断。

```java
public class ProcessController {
    private final List<BusinessProcess> businessProcesses;
    
    public void process(MessageContext context) {
        for (BusinessProcess process : businessProcesses) {
            process.process(context);
            if (context.isNeedBreak()) {
                log.info("Chain broken at {}, traceId={}", 
                    process.getClass().getSimpleName(), 
                    context.getTraceId());
                break;
            }
        }
    }
}
```

**关于异步环节**：当前设计是全同步执行，因为责任链本身是验证逻辑，耗时都在下游发送。如果未来某个环节需要异步 (比如敏感词调用远程 API)，我会：
1. 该 Action 内部使用 `CompletableFuture` 异步执行
2. 在 chain 末尾加一个 `WaitForAsyncAction`，阻塞等待所有异步任务完成
3. 或者改用 Reactor 模式，整个 chain 变成 `Mono<MessageContext>` 流式处理

但考虑到复杂度，当前同步方案 P99 延迟 200ms，满足业务需求，没有过度设计。

**😈 面试官提问 2**：XXL-JOB 分片策略选的什么？为什么？如果某个分片实例宕机了怎么处理？

**🎓 候选人解答**：
我选的是 **CONSISTENT_HASH 分片策略**。原因是定时人群包任务需要保证"同一 CSV 文件始终由同一实例处理"，避免重复发送。CONSISTENT_HASH 根据任务参数 hash 路由，能保证幂等性。

**实例宕机处理**：
1. XXL-JOB 有"失败重试"机制，默认重试 3 次
2. 如果实例彻底宕机，XXL-JOB 会在下一次调度时将任务路由到健康实例
3. 但由于是 CONSISTENT_HASH，路由可能变化，需要业务层保证幂等

**我的幂等设计**：
- 人群包 CSV 每行有唯一 businessId
- 发送前 Redis 检查 `sent:businessId` key，存在则跳过
- Redis key 设置 24h 过期，避免长期占用内存

**延伸**：如果要求更高可用，我会用"广播分片 + 应用层 sharding"：
- XXL-JOB 配置 BROADCAST 策略，所有实例都收到任务
- 应用层根据 businessId % instanceCount 决定谁执行
- 配合 Redis 分布式锁，确保只有一个实例真正执行

但当前方案日均 10 万定时任务，CONSiSTENT_HASH 够用，没上复杂方案。

**😈 面试官提问 3**：ES 索引设计考虑了什么？为什么用 keyword 而不是 text？

**🎓 候选人解答**：
ES 索引设计核心考虑三点：**查询模式**、**存储空间**、**写入性能**。

**字段类型选择**：
- `traceId`/`messageId`/`receiver`：用 `keyword`，因为需要精确匹配 (term query)，不需要分词
- `status`：用 `keyword`，因为要聚合统计 (如"统计各状态消息数")
- `timestamp`：用 `date`，支持 range 查询和日期聚合
- `failReason`：用 `text`，因为可能需要全文检索 (虽然当前场景少)

**keyword vs text 的区别**：
- `keyword`：不分词，整个字段作为一个 term，适合精确匹配、聚合、排序
- `text`：会分词 (如按空格/标点切分)，适合全文检索，但不能用于聚合和排序

**索引参数优化**：
```json
{
  "settings": {
    "number_of_shards": 3,      // 根据数据量预划分
    "number_of_replicas": 1,    // 高可用
    "index.codec": "best_compression", // 压缩，节省 30% 空间
    "index.lifecycle.name": "trace-rollover" // ILM 自动滚动
  }
}
```

**ILM 滚动策略**：
- 每 7 天或 5000 万文档 rollover 到新索引
- 旧索引 30 天后 delete
- 查询时用 `trace-*` alias，自动覆盖所有索引

实际运行下来，单索引 3000 万文档，查询 P99 50ms，满足需求。

### 并发与多线程类 (4 题)

**😈 面试官提问 6**：为什么用虚拟线程而不是线程池？虚拟线程有什么坑？

**🎓 候选人解答**：
**选择虚拟线程的原因**：
1. **线程池的痛点**：需要调 coreSize/maxSize/queueCapacity，调小了吞吐量不够，调大了 OOM
2. **Kafka 消息特点**：每条消息处理耗时不确定 (50ms-3s)，线程池快慢请求互相影响
3. **虚拟线程优势**：按需创建，阻塞不占平台线程，适合 IO 密集型

**我的用法**：
```java
// ConsumeServiceImpl
private final Executor executor = Executors.newVirtualThreadPerTaskExecutor();

@KafkaListener
public void consume(Message message) {
    executor.submit(MdcUtil.wrap(() -> {
        processMessage(message); // 每条消息独立虚拟线程
    }));
}
```

**虚拟线程的坑**：
1. **CPU 密集型不适合**：虚拟线程调度有开销，CPU 密集用平台线程
2. **synchronized 会 pin 平台线程**：Java 21 已优化，但还是要避免
3. **ThreadLocal 泄露**：虚拟线程结束不清理 ThreadLocal 会内存泄漏，我用 `MdcUtil.wrap()` 在 finally 里 MDC.clear()
4. **监控工具不兼容**：传统线程 dump 看不到虚拟线程，需要 jfr 或专门工具

**实际效果**：
- 同样 1000 QPS，平台线程需要 200 个线程 (堆内存 200MB)
- 虚拟线程峰值 5000 个，但只占 20 个平台线程 (堆内存 50MB)
- P99 延迟从 350ms 降到 200ms

**😈 面试官提问 7**：Semaphore 限流和 TokenBucket/RateLimiter 有什么区别？为什么选 Semaphore？

**🎓 候选人解答**：
**三种限流对比**：

| 算法 | 原理 | 适用场景 |
|------|------|----------|
| Semaphore | 计数器，固定 permits，用完即止 | 保护资源 (如 DB 连接池) |
| Guava RateLimiter | 令牌桶，按固定速率生产令牌 | 平滑限流 (如 API 调用) |
| Redis TokenBucket | 分布式令牌桶，支持集群限流 | 多实例统一限流 |

**我选 Semaphore 的原因**：
1. **场景是"保护下游"不是"平滑流量"**：短信网关 QPS 上限 1000，超过直接拒绝，不需要平滑
2. **快速失败**：`tryAcquire()` 立即返回 false，调用方立刻知道系统饱和，可降级或重试
3. **零依赖**：JDK 内置，不需要引入 Guava 或 Redis

**代码对比**：
```java
// Semaphore：用完即止
if (!semaphore.tryAcquire()) {
    throw new SystemBusyException(); // 立即 429
}

// Guava RateLimiter：阻塞等待 (不适合我)
rateLimiter.acquire(); // 可能阻塞几秒，消息堆积
```

**未来改进**：
如果需要多实例统一限流 (如单机 1000，集群 10 台共 10000)，我会用 **Redis Lua 脚本实现分布式 Semaphore**：
- key: `rate:limit:semaphore`
- acquire: Lua 原子递减，<0 拒绝
- release: Lua 原子递增

但当前单机 QPS 够用，没上分布式限流。

**😈 面试官提问 8**：背压机制的水位阈值怎么定的？500/200 是拍脑袋吗？

**🎓 候选人解答**：
**不是拍脑袋，是基于压测数据**：

**压测过程**：
1. 用 JMeter 模拟 5000 QPS 持续发送
2. 观察 in-flight 计数和 P99 延迟
3. 发现 in-flight > 600 时，P99 从 200ms 飙升到 800ms (GC 压力)
4. in-flight < 150 时，系统资源利用率不足 30%

**阈值设定**：
- **HIGH = 500**：留 100 缓冲，避免频繁触发
- **LOW = 200**：滞后 300，避免"震荡"(刚恢复又触发)

**滞后的意义**：类似空调温控，26 度开/24 度关，避免频繁启停。

**监控验证**：
Grafana 配置告警：
```promql
# 背压触发持续 1 分钟告警
austin.backpressure.in_flight > 400 for 1m

# 背压长时间不恢复告警
austin.backpressure.paused == 1 for 5m
```

**未来优化**：

- 成功发送 → permits += 1% (slow start)
- 遇到 429/超时 → permits /= 2 (fast decay)
- 动态适配下游实际承载能力

类似 TCP 拥塞控制，但需要更多压测数据验证。

**😈 面试官提问 9**：Future 超时怎么处理？如果虚拟线程卡住了怎么办？

**🎓 候选人解答**：
**当前方案：同步阻塞 + 线程级超时**

```java
// SendMessageAction 调用下游

        // HttpClient 设置 socketTimeout=3000ms
```

**虚拟线程卡住的极端情况**：
- 下游 HTTP 服务端不返回 (如死锁)
- HttpClient 的 socketTimeout 不生效 (bug)
- 虚拟线程永久阻塞，in-flight 计数不释放

**我的兜底方案**：
1. **BackPressureManager 强制超时**：
```java
// 每 5 秒检查一次 in-flight 超过 10 分钟的线程
scheduledExecutor.scheduleAtFixedRate(() -> {
    long staleThreads = inFlightThreads.stream()
        .filter(t -> System.currentTimeMillis() - t.startTime > 10*60*1000)
        .count();
    if (staleThreads > 0) {
        log.error("Detected {} stale threads, alerting!", staleThreads);
        // 触发告警，人工介入

}, 5, 5, TimeUnit.SECONDS);
```

**😈 面试官提问 10**：Kafka 如何保证消息不丢失？你的 auto-commit=true 不是有风险吗？

**🎓 候选人解答**：
**先坦白：auto-commit=true 确实有重复消费风险**，但我做了**幂等设计**兜底。

**Kafka 消息丢失的三个场景及应对**：

| 场景 | 风险 | 我的方案 |
|------|------|----------|
| 生产者发送失败 | 消息没到 Broker | 重试 3 次 + 异常告警 |
| Broker宕机 | 消息没同步到 Follower | 配置 acks=all, min.insync.replicas=2 |
| 消费者提交 offset 后宕机 | 消息已提交但未处理完 | **幂等设计 (见下)** |

**我的幂等设计**：
```java
// 发送前 Redis 检查 businessId
String key = "sent:" + context.getBusinessId();
Boolean exists = redisTemplate.opsForValue().setIfAbsent(key, "1", 24, TimeUnit.HOURS);
if (Boolean.FALSE.equals(exists)) {
    log.info("Duplicate message, skipping, businessId={}", context.getBusinessId());
    return; // 幂等跳过
}
```

**为什么用 auto-commit=true 而不是手动 commit**：
- 手动 commit 需要在 `processMessage()` 成功后提交 offset
- 但如果 commit 后宕机，消息已处理但下游可能没收到 (下游有自己的重试)
- auto-commit 虽然可能重复，但配合幂等设计，影响可控

**延伸**：如果要 exactly-once，需要**端到端幂等**：
1. Kafka 事务 (Producer + Consumer 原子提交)
2. 下游网关幂等 (如短信服务商的 businessId 去重)
3. 当前方案是"至少一次 + 业务幂等"，工程上够用

**监控**：
- Prometheus 暴露 `austin.kafka.message.consumed{status="success/failure"}`
- Grafana 计算重复率 = (consumed - unique businessId) / consumed

当前重复率 < 0.1%，在可接受范围。

**😈 面试官提问 11**：ES 的 collapse 查询具体怎么用？什么场景下用？

**🎓 候选人解答**：
**collapse 的作用**：对某个字段去重，只返回每个值的最新/最旧一条文档。

**我的场景**：按 receiver 查询时，希望"一个手机号的多条消息只显示最新一条状态"。

**ES 查询 DSL**：
```json
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "receiver": "138xxxx1234" }},
        { "range": { "timestamp": { "gte": "2024-03-29T20:00:00Z" }}}
      ]
    }
  },
  "collapse": {
    "field": "messageId",        // 按 messageId 去重
    "inner_hits": {
      "name": "latest",
      "size": 1,
      "sort": [{ "timestamp": "desc" }]  // 只返回 timestamp 最大的
    }
  },
  "sort": [{ "timestamp": "desc" }]
}
```

**返回结果**：
```json
{
  "hits": [
    {
      "_source": { "messageId": "msg_001", "status": "SENT", ... },
      "inner_hits": {
        "latest": {
          "hits": [{ "_source": { ... } }]  // 这就是最新一条
        }
      }
    }
  ]
}
```

**对比方案**：
- **不用 collapse**：查出所有记录，应用层按 messageId 分组取最新 → 内存爆炸
- **用 collapse**：ES 内部去重，网络传输减少 90%

**限制**：
- collapse 只能嵌套一层 inner_hits
- 不能和 aggregation 同时用
- 字段必须是 single-value (不能是 array)

实际压测：100 万文档，collapse 查询 P99 80ms，无 collapse P99 500ms + OOM。

**😈 面试官提问 12**：Redis 滑动窗口去重的 Lua 脚本怎么写？为什么用 ZSET 而不是 List？

**🎓 候选人解答**：
**Lua 脚本**：
```lua
-- KEYS[1]: dedup:slice:{templateId}:{receiver}
-- ARGV[1]: windowSize (秒，如 60)
-- ARGV[2]: threshold (阈值，如 5)
-- ARGV[3]: currentTimestamp

local key = KEYS[1]
local windowSize = tonumber(ARGV[1])
local threshold = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

-- 1. 移除窗口外元素 (score < now - windowSize)
redis.call('ZREMRANGEBYSCORE', key, '-inf', now - windowSize)

-- 2. 统计窗口内元素数量
local count = redis.call('ZCARD', key)

-- 3. 超过阈值，拒绝插入
if count >= threshold then
    return 0
end

-- 4. 插入当前元素 (score=timestamp, value=timestamp 唯一)
redis.call('ZADD', key, now, now)

-- 5. 设置过期时间 (windowSize + 缓冲)
redis.call('EXPIRE', key, windowSize + 60)

return 1
```

**Java 调用**：
```java
public boolean allow(String key, int windowSize, int threshold) {
    Long result = redisTemplate.execute(
        script,
        Collections.singletonList(key),
        String.valueOf(windowSize),
        String.valueOf(threshold),
        String.valueOf(System.currentTimeMillis())
    );
    return result == 1;
}
```

**为什么用 ZSET 而不是 List**：
| 维度 | ZSET | List |
|------|------|------|
| 移除过期元素 | `ZREMRANGEBYSCORE` O(log N) | 需要遍历 O(N) |
| 统计数量 | `ZCARD` O(1) | `LLEN` O(1) |
| 去重 | score 天然去重 | 需要应用层判断 |
| 时间复杂度 | O(log N) | O(N) |

**关键点**：
- ZSET 的 `score` 和 `value` 都用 timestamp，score 用于排序，value 用于去重
- `EXPIRE` 设置冗余 60 秒，防止 Lua 执行期间过期
- 阈值建议 windowSize * QPS * 1.2，留 20% 缓冲

**压测数据**：
- Redis 单实例 QPS 8000+
- Lua 脚本 P99 2ms
- 内存：100 万去重 key，约 500MB

**😈 面试官提问 13**：缓存一致性怎么保证？Caffeine + Redis 双层会不会不一致？

**🎓 候选人解答**：
**先承认：双层缓存确实有一致性问题**，但我的场景是"消息模板配置"，容忍分钟级延时。

**我的缓存策略**：
```java
// Caffeine LocalCache (5000 容量/10min TTL)
LoadingCache<Long, MessageTemplate> localCache = Caffeine.newBuilder()
    .maximumSize(5000)
    .expireAfterWrite(10, TimeUnit.MINUTES)
    .build(key -> loadFromRedis(key));

// 查询逻辑
public MessageTemplate getTemplate(Long id) {
    return localCache.get(id); // 优先 LocalCache
}

// 更新逻辑
public void updateTemplate(MessageTemplate template) {
    messageTemplateRepository.save(template); // 写 DB
    redisTemplate.delete("template:" + template.getId()); // 删 Redis
    redisTemplate.convertAndSend("template:change", template.getId()); // Pub/Sub
}

// 监听 Redis 通知，清除 LocalCache
@RedisListener("template:change")
public void onTemplateChange(Long templateId) {
    localCache.invalidate(templateId); // 清除 LocalCache
}
```

**一致性分析**：
| 场景 | 一致性 | 影响 |
|------|--------|------|
| 更新后立即查询 | 10min 内 LocalCache 旧数据 | 运营修改模板后，部分用户看到旧模板 (可接受) |
| Redis 宕机 | LocalCache 继续服务 | 高可用，10min 后降级到 DB |
| 多实例不一致 | A 实例更新，B 实例 10min 后才感知 | Redis Pub/Sub 有网络延迟，但 10min TTL 兜底 |

**如果要求强一致**：
- 方案 1：只用 Redis 缓存，不要 LocalCache (增加 Redis 压力)
- 方案 2：更新时广播所有实例清空 LocalCache (依赖网络可靠性)
- 方案 3：用 Redis + WebSocket 实时推送 (复杂度高)

**我的选择**：模板配置变更频率低 (每天<10 次)，10min 不一致可接受，优先保证性能。

**监控**：
- Prometheus 暴露 `austin.cache.local.hit_rate`
- 告警：命中率 < 80% 持续 5 分钟 (可能被击穿)

**😈 面试官提问 15**：如何监控 Kafka 消费延迟？延迟高了怎么告警？

**🎓 候选人解答**：
**监控指标**：
```promql
# austin.kafka.consumer.lag (Gauge)
# 计算方式：consumer 定期查询 Kafka offset - committed offset
public class KafkaLagCollector {
    private final KafkaConsumer<String, String> consumer;
    
    @Scheduled(fixedRate = 5000) // 每 5 秒采集
    public void collect() {
        Map<TopicPartition, Long> endOffsets = consumer.endOffsets(partitions);
        Map<TopicPartition, Long> committed = consumer.committed(partitions);
        
        for (TopicPartition tp : partitions) {
            long lag = endOffsets.get(tp) - (committed.get(tp) != null ? committed.get(tp) : 0);
            lagGauge.set(lag, tp.topic(), tp.partition(), groupId);
        }
    }
}
```

**Grafana 告警规则**：
```promql
# 延迟 > 1000 持续 2 分钟告警
austin.kafka.consumer.lag{groupId="austin-consumer-group"} > 1000 for 2m

# 延迟增长率 > 100/s (说明在恶化)
deriv(austin.kafka.consumer.lag[1m]) > 100
```

**延迟高的排查流程**：
1. **看 Prometheus**：确认是哪个 groupId/topic lag 高
2. **看消费者日志**：Loki 查 `groupId=xxx AND level=ERROR`，看是否有异常
3. **看背压指标**：`austin.backpressure.paused` 是否触发
4. **看下游网关**：短信服务商是否限流/超时

**优化手段**：
- 增加消费者实例 (Kafka 消费者组水平扩展)
- 优化消费逻辑 (如批量发送，减少下游调用次数)

**当前阈值**：
- 延迟 > 500：Warning (企业微信通知)
- 延迟 > 1000：Critical (电话告警)
- 延迟增长率 > 100/s：P0 (立即响应)

**😈 面试官提问 19**：告警策略怎么设计？如何避免告警风暴？

| 级别 | 触发条件 | 通知方式 | 响应时间 |

| P2 | 次要指标异常 (如缓存命中率<80%) | 邮件 | 24 小时 |

**告警规则示例**：
```yaml

        expr: austin.kafka.consumer.lag > 1000
        for: 2m

          severity: P1
        annotations:
          summary: "Kafka lag {{ $value }} > 1000"
      
      # P1: 背压触发

      - alert: CacheHitRateLow
        expr: austin.cache.local.hit_rate < 0.8
        for: 5m
        labels:
          severity: P2
```

**避免告警风暴**：
1. **分组聚合**：相同 alertname 的告警合并成一条通知
2. **抑制规则**：P0 告警触发时，抑制相关 P1/P2 告警
   ```yaml
   inhibit_rules:
     - source_match:
         severity: P0
       target_match:
         severity: P1
       equal: [alertname]
   ```
3. **静默规则**：维护窗口期间静默告警
4. **去重**：相同告警 1 小时内只通知一次

**当前效果**：
- 日均告警：P0 < 1 次，P1 < 5 次，P2 < 20 次
- 告警疲劳：无 (工程师不会忽略告警)

## 六、进阶防守：数据口径与未来演进

### 1. 虚拟量化数据口径

**面试场景**：当面试官问"你的系统 QPS 多少？数据量多大？"时，用以下口径：

| 指标 | 数值 | 说明 |
|------|------|------|
| **单机 QPS** | 2000-5000 | Java 21 虚拟线程 + 三层背压防护压测数据 |
| **ES 日增文档** | 500-1000 万 | 每条消息 2-3 条 Trace (发送 + 成功/失败)，日均 300 万消息 |
| **Kafka partitions** | 6-12 per topic | 根据消费者实例数动态调整，当前 3 实例×2 副本 = 6 |
| **P99 延迟** | ~200ms | 从接收请求到发送完成，下游网关耗时占比 60% |
| **Semaphore permits** | 1000 (动态) | 从 Nacos 获取，支持热更新，多实例需分布式限流 |
| **背压水位** | high=500, low=200 (动态) | AIMD 自适应调整，基于 RT 实时优化 |
| **Nacos 配置项** | ~50 个 | 限流阈值/去重窗口/盾牌时段等，秒级热更新 |
| **Redis 去重 key 数** | 100-200 万 | 按 receiver+templateId 维度，TTL 24h |
| **Loki 日增日志** | 50-100GB | 每条消息 5-10 条日志，JSON 压缩后约 500 bytes/条 |
| **Prometheus 指标数** | ~200 个 | 低基数 Label，内存占用 < 500MB |
| **XXL-JOB 日调度** | 10-20 万次 | 人群包定时任务，CONSISTENT_HASH 分片 |

**注意事项**：
- 不要说"支持 10 万 QPS"(太假)，说"单机 2000-5000，可水平扩展"
- 不要说"零丢失"，说"至少一次 + 幂等设计，重复率<0.1%"
- 不要说"毫秒级延迟"，说"P99 200ms，P50 80ms"

**如果面试官追问"怎么压测的"**：
> 用 JMeter 模拟 HTTP 请求，5000 线程持续发送 10 分钟，观察 Prometheus 指标和 Grafana 面板。压测环境：4 核 8G 虚拟机，MySQL 8 核 16G，Kafka 3 节点集群。

### 2. 超纲防御 (未来优化方向)

**面试场景**：当面试官问"如果流量翻 10 倍，你怎么办？"或"项目还有什么改进空间？"时，抛出以下方向：

---

**方向 1：Redis 全局去重 (跨实例一致性)**

**当前问题**：单机 Redis 去重，多实例场景下同一消息可能被不同实例重复发送。

**解决方案**：Redis Cluster + Redisson 分布式锁
```java
// 全局去重
RLock lock = redisson.getLock("dedup:global:" + businessId);
if (lock.tryLock(0, 24, TimeUnit.HOURS)) {
    try {
        // 检查 + 发送
        sendMessage();
    } finally {
        lock.unlock();
    }
}
```

**代价**：网络 RT 增加 5-10ms，QPS 下降 20%。

**适用场景**：对重复零容忍 (如金融通知)，当前业务容忍<0.1% 重复，没必要。

---

**方向 2：延迟队列 + 指数退避重试**

**当前问题**：下游网关超时/限流时，消息直接失败，没有重试机制。

**解决方案**：RocketMQ 延迟队列 + 指数退避
```java
// 发送失败后重试
int retryCount = message.getRetryCount();
long delaySeconds = (long) Math.pow(2, retryCount); // 1, 2, 4, 8, 16...
rocketMQTemplate.send("retry-topic", message, delaySeconds);
```

**退避策略**：
- 第 1 次重试：1 秒后
- 第 2 次重试：2 秒后
- 第 3 次重试：4 秒后
- 第 4 次重试：8 秒后
- 第 5 次重试：16 秒后 → 仍失败则告警人工介入

**代价**：需要引入 RocketMQ (Kafka 不支持精确延迟)，增加运维成本。

---

**方向 3：Flink 实时 analytics (送达率监控)**

**当前问题**：送达率 = 成功数/发送数，需要 T+1 离线统计，无法实时发现问题。

**解决方案**：Flink 消费 Kafka，实时计算各渠道/模板的送达率
```java
// Flink 任务
DataStream<TraceInfo> traces = env.addSource(kafkaSource);
traces
    .keyBy(TraceInfo::getChannelType)
    .window(TumblingEventTimeWindows.of(Time.MINUTES))
    .process(new DeliveryRateProcessFunction())
    .addSink(prometheusSink); // 输出到 Prometheus
```

**Prometheus 指标**：
```promql
austin.delivery.rate{channel="sms", templateId="1001"}
```

**告警**：送达率 < 95% 持续 5 分钟 → P1 告警。

**代价**：需要单独部署 Flink 集群，运维复杂度增加。

---

**方向 4：Vue3 + TypeScript 前端重构**

**当前问题**：前端 Vue2 + jQuery 混合，代码难以维护，缺少类型安全。

**解决方案**：Vue3 + Vite + TypeScript + Pinia
```typescript
// 类型安全 API 调用
const { data: templates } = useSwr(
    '/api/messageTemplate/list',
    (url) => fetch<MessageTemplate[]>(url)
);

// 模板类型
interface MessageTemplate {
    id: number;
    name: string;
    channelId: number;
    // ...
}
```

**收益**：
- 编译期类型检查，减少 50% 前端 bug
- Vite 热更新，开发体验提升
- Composition API，逻辑复用更方便

**代价**：需要 2-3 周重构，当前业务迭代快，优先级低。

---

**方向 5：OpenTelemetry 全链路集成**

**当前问题**：ES 追踪是"哑巴 trace"，没有 Span 层级关系，无法可视化调用链。

**解决方案**：OpenTelemetry SDK + Jaeger/Tempo
```java
// 自动埋点
@Bean
public OpenTelemetry openTelemetry() {
    return OpenTelemetry.builder()
        .addSpanProcessor(BatchSpanProcessor.create(exporter))
        .build();
}

// 手动创建 Span (跨 Kafka 边界)
Span span = tracer.spanBuilder("processMessage")
    .setSpanKind(SpanKind.CONSUMER)
    .setParent(Context.current().with(baggedSpanContext))
    .startSpan();
try (Scope scope = span.makeCurrent()) {
    processMessage(message);
} finally {
    span.end();
}
```

**可视化**：Grafana Tempo 展示完整调用链
```
HTTP Request → ProcessController → ShieldAction → DeduplicationAction → Kafka → Consumer → Handler → Downstream
   (50ms)           (10ms)            (5ms)            (20ms)           (2ms)   (100ms)      (100ms)
```

**收益**：
- 一眼看出瓶颈环节
- 自动关联 logs/metrics/traces
- 支持 P99 延迟下钻分析

**代价**：需要学习 OTel 协议，改造现有埋点，预计 2 周工作量。

---
