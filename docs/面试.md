## 一、项目介绍（3个版本，按面试阶段切换）

### 版本 A（简历 3~4 行，量化版）

- 参与建设企业级消息推送平台 Austin，统一承接短信、邮件、企微、钉钉、公众号等多渠道消息发送，支持高并发异步投递。
- 设计并落地双层 Pipeline（API 入站 + Handler 出站），结合 Semaphore 全局限流、消费者虚拟线程背压，保障峰值下系统稳定性。
- 完善可观测体系：Micrometer + Prometheus + Grafana 指标监控，Loki 结构化日志（MDC `traceId`）实现全链路检索。
- 打通消息追踪闭环：基于 `messageId/businessId/user` 三维链路聚合（`/trace/*`），支持消息状态回溯与故障快速定位。

### 版本 B（面试官追问时 2 分钟技术版）

Austin 是一个高并发消息推送平台，核心目标是：
1) 统一消息发送入口；
2) 渠道隔离与高可用投递；
3) 可追踪、可观测、可排障。

在架构上分两层：
- **API 层 Pipeline**：参数校验、模板组装、业务校验、发送 MQ（`SendMqAction`）。
- **消费层 Pipeline**：丢弃检查、夜间屏蔽、去重、敏感词、渠道发送。

在稳定性上采用三道防线：
- **入口防线**：MQ 发送前全局 Semaphore 限流 + pending timeout 超时熔断。
- **消费防线**：虚拟线程并发 + `VirtualThreadBackPressureManager` 动态 pause/resume。
- **渠道防线**：渠道级限流与失败隔离，避免单通道雪崩扩散。

在可观测上，HTTP 入口 `MdcEnrichFilter` 注入 `traceId`，Kafka 头透传，消费端 `MdcInterceptor` 还原。  
`logback-spring.xml` 输出 JSON 日志（包含 `traceId/templateId/messageId/businessId/kafkaGroupId/xxlJobId`），可在 Loki/ES 做字段级检索。  
同时通过 `TraceService` + `DataController` 对外提供 `/trace/message`、`/trace/user`、`/trace/messageTemplate`、`/trace/sms` 查询能力。

### 版本 C（自我介绍口播 60 秒）

我做的是 Austin 消息推送平台。它把短信、邮件、企微这些消息统一收口，用 API 层和消费层两段责任链完成消息处理。为了应对高并发，我在入口做了 Semaphore 限流、在消费端做了虚拟线程背压，避免 Kafka 积压把下游打崩。另一个重点是链路追踪：我们在 HTTP、MQ、消费、渠道全链路透传 traceId，并把日志结构化到 Loki，同时维护 messageId/businessId/user 三个维度的链路数据，出现“某条消息没到达”的问题时可以在几分钟内定位到具体失败节点。

## 二、技术架构一图流（面试答题骨架）

```
Client
  -> MdcEnrichFilter(traceId/path/userId/requestIp)
  -> API Pipeline(PreCheck -> Assemble -> AfterCheck -> SendMqAction)
  -> Kafka Topic: austinBusiness
  -> Consumer(MdcInterceptor restore traceId)
  -> Handler Pipeline(Discard -> Shield -> Dedup -> SensWords -> SendMessage)
  -> Channel Script(SMS/Email/WeChat/...)
  -> LogUtils Anchor 打点 -> austinTraceLog
  -> Flink(austin-stream) -> Redis链路聚合
  -> /trace/* 查询接口 + Loki/ES 日志检索 + Grafana 指标告警
```

## 三、项目亮点（12 条可选，按简历篇幅择优使用）

> 你可以挑 10~15 条中的任意子集放简历。下面给 12 条可替换亮点。

1. **双层责任链设计**：API 与消费层各自使用 Pipeline，职责清晰、扩展节点成本低。
2. **入口全局限流**：`SendMqAction` + `MqRateLimiter` 控制瞬时写 MQ 速率，防止洪峰冲垮后端。
3. **超时快速失败**：Pending 超时阈值（`austin.mq.pending-timeout-ms`）防止长队列导致雪崩。
4. **虚拟线程消费模型**：消费者使用 `newVirtualThreadPerTaskExecutor`，提升 I/O 密集场景并发承载。
5. **动态背压闭环**：`VirtualThreadBackPressureManager` 结合 RT 传感器实现 pause/resume，抑制 Lag 失控。
6. **MDC 全链路透传**：HTTP 注入、Kafka Header 传递、消费端恢复，trace 上下文无缝衔接。
7. **结构化日志工程化**：Logback JSON 输出关键字段，Loki/ES 支持按 `traceId/messageId/businessId` 秒级检索。
8. **多维链路追踪能力**：按 messageId、user、template、sms 维度查询，支持运营与研发双视角回溯。
9. **状态语义清晰**：`AnchorState` 明确建模接收/丢弃/屏蔽/去重/成功/失败/点击等关键阶段。
10. **可观测体系完整**：API 耗时 P50/P95/P99、错误率、Kafka 消费成功/失败计数、处理时长均可监控。
11. **缓存抗压实践**：Caffeine + Redis 缓存策略降低模板查询开销，支撑高并发读取。
12. **压测工具链完善**：提供 k6 压测脚本与性能排障手册（JVM/Kafka/连接池），定位路径标准化。

## 四、重点能力：消息链路追踪（本项目核心卖点）

### 4.1 追踪主线（代码对齐）

- **入口注入**：`MdcEnrichFilter`（最高优先级）生成/透传 `X-Trace-Id`，并写回响应头。
- **消息透传**：`KafkaSendMqServiceImpl` 将 `traceId`（及 `xxlJobId`）写入 Kafka Header。
- **消费恢复**：`MdcInterceptor` 从 Header 恢复 MDC，消费完 `afterRecord()` 清理，避免污染。
- **线程传播**：`MdcUtil.wrap(...)` 在虚拟线程执行任务时保持上下文连续。
- **字段落盘**：`logback-spring.xml` 统一输出 JSON 日志，固定包含 `traceId/templateId/messageId/businessId/kafkaGroupId/xxlJobId`。

### 4.2 追踪数据面（业务可见）

- Trace 事件通过 `AnchorInfo` 打点流入 `austinTraceLog`。
- Flink `AustinSink` 聚合后落 Redis：
  - `Austin:MessageId:{messageId}`：单消息链路（3天 TTL）
  - `receiver`：用户维度链路（当天 TTL）
  - `businessId`：模板维度状态统计（30天 TTL）
- `DataController` 对外提供：
  - `/trace/message`（按 messageId）
  - `/trace/user`（按接收人）
  - `/trace/messageTemplate`（按业务维度）
  - `/trace/sms`（按手机号+日期）

### 4.3 Loki + ES 双通路排障策略

- **Loki 主通路**：适合实时排障，按 MDC 字段快速过滤。
- **ES 辅助通路**：将同一份 JSON 日志接入 ELK（Filebeat/Logstash）后，可做长周期聚合分析与复盘报表。

> 说明：代码内已具备结构化日志与链路字段，ES 通路通常由日志采集链路配置完成（不要求业务代码改动）。

## 五、消息发送全流程（面试必答标准稿）

### 5.1 成功路径（从请求到用户触达）

1. **HTTP 入站**：请求到达 Web 层，`MdcEnrichFilter` 注入 `traceId` 等 MDC 字段。  
2. **API Pipeline**：预检/组装/后检完成后，`SendMqAction` 执行限流与超时校验。  
3. **发送 MQ**：`KafkaSendMqServiceImpl` 将消息写入 `austinBusiness`，并携带 `traceId` Header。  
4. **Kafka 消费**：消费者拉取消息，`MdcInterceptor` 恢复 trace 上下文。  
5. **Handler Pipeline**：依次执行丢弃、屏蔽、去重、敏感词，再进入渠道发送节点。  
6. **渠道发送**：对应 Handler/Script 调用短信或其他渠道接口。  
7. **打点沉淀**：关键状态通过 `AnchorInfo` 写日志/链路流，Flink 聚合到 Redis。  
8. **查询展示**：通过 `/trace/*` 与 Loki/ES 检索实现“业务可见 + 技术可定位”。

### 5.2 失败路径（某条消息未触达怎么排查）

> 场景：用户反馈 messageId=xxx 未收到短信。

**步骤 A：先看业务链路状态（最快）**
1. 调 `/trace/message` 查该 messageId 状态序列。
2. 若停在去重/屏蔽状态：属于策略拦截，非渠道故障。
3. 若到 `SEND_FAIL`：进入技术排障流程。

**步骤 B：Loki 实时排障（分钟级）**
1. 先按 `messageId` 或 `traceId` 过滤日志。  
2. 对照时间线确认卡点：
   - 是否成功写入 Kafka？
   - 消费端是否执行到 `SendMessageAction`？
   - 渠道调用返回码/异常是什么？
3. 结合 `kafkaGroupId` 判断是否消费组局部异常（rebalance、背压暂停等）。

**步骤 C：ES 深度排障（小时/天级复盘）**
1. 在 ES 按 `messageId/businessId/templateId` 聚合同批次失败分布。  
2. 观察同模板、同渠道是否集中失败（定位通道/配置问题）。  
3. 基于时间窗口统计失败率突变点，与发布记录/配置变更对齐。

**步骤 D：闭环动作**
- 渠道侧故障：切备通道 + 失败重试。  
- 策略误杀：修正规则/模板配置。  
- 消费拥塞：调整背压阈值、扩容消费者、优化慢节点。

## 六、模拟面试 Q&A（20 题，覆盖架构/稳定性/追踪/排障）

### Q1：为什么选 Kafka 作为核心消息队列？
A：高吞吐、可重放、消费者组扩展能力强，适合推送平台削峰与异步解耦。

### Q2：如何保证消息不丢？
A：生产端 `acks=all` + 重试/幂等机制，消费端 at-least-once 语义并结合去重，整体保障“至少一次 + 业务幂等”。

### Q3：你们如何做幂等防重复发送？
A：在去重节点按模板/接收人/内容指纹/时间窗口生成幂等键，落 Redis 并配置 TTL。

### Q4：双层 Pipeline 的价值是什么？
A：API 负责请求合法性和入队，Handler 负责投递策略与渠道执行；边界清晰、扩展低耦合。

### Q5：新增一个黑名单节点要改哪里？
A：新增 `BusinessProcess` 实现并在对应 `ProcessTemplate` 注册，既有节点无需改动。

### Q6：为什么使用虚拟线程？
A：消费场景 I/O 等待多，用虚拟线程提高并发密度；但资源治理仍依赖限流与背压。

### Q7：虚拟线程会不会把下游打爆？
A：会，所以我们保留 Semaphore、Token Bucket、背压 pause/resume，限制真实下游压力。

### Q8：遇到 Kafka Lag 快速上涨怎么处理？
A：先看 `fetch rate` 与消费者状态，再看慢节点 RT 和背压水位，必要时扩容实例/分区并隔离慢通道。

### Q9：`traceId` 在链路中如何传递？
A：HTTP 入站写 MDC -> Kafka Header 透传 -> 消费端恢复 MDC -> 日志落盘，贯穿全链路。

### Q10：为什么要强调结构化日志？
A：文本日志难做精确检索；JSON + MDC 字段可在 Loki/ES 按字段过滤，定位速度提升明显。

### Q11：`messageId`、`businessId`、`traceId` 三者怎么分工？
A：`traceId` 跟踪一次请求上下文；`messageId` 唯一标识单条消息；`businessId` 关联模板与统计维度。

### Q12：如何做“某条消息未触达”的快速排查？
A：先查 `/trace/message` 判断停在哪个状态，再用 Loki 按 `messageId/traceId` 查异常节点，最后用 ES 看批量分布。

### Q13：Loki 与 ES 的定位差异？
A：Loki 适合实时日志排障；ES 适合复杂聚合分析、长期趋势、失败画像。

### Q14：缓存一致性怎么做？
A：L1 Caffeine + L2 Redis + TTL 兜底，模板变更后主动失效，兼顾性能与一致性。

### Q15：API 层有哪些关键监控？
A：请求总量、错误率、P50/P95/P99 延迟（`ApiMetricsFilter` 采集），支持告警阈值配置。

### Q16：消费侧关键监控有哪些？
A：按 group 的成功/失败计数、处理耗时分位、Kafka Lag、背压状态（pause/resume）。

### Q17：如果第三方短信通道抖动怎么办？
A：通道级限流 + 失败重试 + 备用通道切换，并通过链路追踪确认失败集中区间。

### Q18：如何验证系统容量上限？
A：用 k6 压测脚本分场景升压，观察错误率、P99、Lag、GC、连接池等待，找到稳态拐点。

### Q19：如何兼顾可靠性与吞吐？
A：核心是“异步解耦 + 分层限流 + 幂等去重 + 可观测闭环”，在 SLA 与成本间做可配置权衡。

### Q20：你觉得这个项目最有价值的能力是什么？
A：不是“发出去”本身，而是“发出去且可追踪、失败可定位、问题可复盘”，这是平台化能力壁垒。

## 七、未来优化方向（12 条，覆盖架构/追踪/可靠性/成本）

1. **Outbox + CDC**：收敛业务落库与 MQ 投递之间的一致性窗口。
2. **延时重试队列**：失败消息指数退避，降低主链路阻塞。
3. **死信队列治理**：失败原因分类、自动告警、人工回放工具化。
4. **优先级队列与租户配额**：保障验证码/风控消息优先级。
5. **多通道路由引擎**：按成功率与 RT 动态选择最优通道。
6. **规则引擎 DSL 化**：把屏蔽、去重、黑名单变为可配置策略。
7. **链路画像中心**：按模板/渠道/地域输出失败热力图与归因。
8. **Loki + ES 联合看板**：实时与离线报表统一展示。
9. **自动化故障处置**：触发阈值后自动降速、切备、暂停高风险模板。
10. **全链路压测平台化**：持续压测基线，防止性能回退。
11. **成本治理**：按消息类型与时段做弹性扩缩容与通道成本优化。
12. **A/B 发送策略实验**：不同文案/发送时机的效果对比，形成数据驱动优化。
