# Austin 消息推送平台 - 简历与面试冲刺宝典

## 一、 项目描述 (Project Descriptions)

### 1. 简历书写版 (STAR法则)

- **基于 Spring Boot + Kafka + Redis 独立设计并实现**高并发消息推送平台，支持短信、邮件、企业微信、钉钉等 8 种渠道，单机峰值 QPS 达 **3,500+**，消息端到端 P99 延迟控制在 **120ms** 以内。
- **设计并实现两级责任链 Pipeline**（API 层 4 节点 + Handler 层 5 节点），涵盖参数预校验、模板组装、夜间屏蔽、内容去重及敏感词过滤，新增渠道或规则节点只需实现 `BusinessProcess` 接口并注册到 `ProcessTemplate`，**零侵入扩展**，需求响应时间从数小时压缩至 **30 分钟**内。
- **引入 Caffeine L1 + Redis L2 两级缓存**，消息模板命中率达 **98%**，DB 查询量下降 **90%**；利用 Semaphore 信号量（1,000 许可）对 Kafka 入队进行背压控制，结合 Token Bucket 实现渠道级限流，在第三方下游限速时有效防止雪崩。
- **搭建 Prometheus + Grafana + Loki 全链路可观测体系**，自定义 HTTP P99 延迟、Kafka 消费者 Lag、MQ 信号量水位等核心指标；通过 MDC 注入 `traceId` 并透传至 Kafka 消息头，日志全链路关联，线上问题排查时间从 **30 分钟**缩短至 **5 分钟**。

### 2. 详细描述版 (自我复盘用)

**项目背景：**  
Austin 是一个统一消息推送平台，解决业务方对接多渠道（短信、邮件、企业微信、公众号、小程序、钉钉、飞书、Push 通知）时代码重复、管理混乱的痛点。业务方只需调用统一 HTTP 接口，传入 `templateId` 和目标用户列表，平台负责下游渠道路由、限流、去重、可观测性等所有横切关注点。

**核心业务链路（从接收请求到用户收到消息）：**

```
HTTP 请求 (POST /api/send)
    │
    ▼
[API 层 - Pipeline 1]
    ① SendPreCheckAction      ← 参数合法性校验、模板状态验证（Caffeine L1 + DB）
    ② SendAssembleAction      ← 解析模板变量，构建 List<TaskInfo>，记录消息元数据
    ③ SendAfterCheckAction    ← 下游渠道账号可用性二次校验（ChannelAccountCaching）
    ④ SendMqAction            ← Semaphore.tryAcquire() 背压 → KafkaProducer 写入
                                  `austinBusiness` Topic（acks=all, 幂等写入）
    │
    ▼ Kafka 消费
[Handler 层 - Pipeline 2]（每条 TaskInfo 独立处理）
    ① DiscardAction           ← 检查消息是否超时/模板已停用，丢弃无效消息
    ② ShieldAction            ← 夜间免打扰（用户设置窗口期），超出则推入 Redis
                                  Sorted Set 延迟处理
    ③ DeduplicationAction     ← Redis Set 内容去重（可配置 TTL）
    ④ SensWordsAction         ← 敏感词过滤
    ⑤ SendMessageAction       ← HandlerHolder.route(channelType) → 调用对应渠道
                                  Handler（如 SmsHandler）→ 调用第三方 API
    │
    ▼
第三方渠道 API（阿里云短信、SendGrid、微信开放平台等）
    │
    ▼
用户收到消息
```

**关键工程细节：**

- **Kafka 生产者** 开启 `acks=all`、`enable.idempotence=true`、`retries=3`，结合 Snappy 压缩与 64KB batch size，兼顾可靠性与吞吐量。
- **Kafka 消费者** 按渠道类型分 Consumer Group，通过 `KafkaConfiguration` 动态注册 `@KafkaListener`，Header 过滤器确保每条消息只被匹配的 Group 消费。
- **虚拟线程（Java 21+）**：`spring.threads.virtual.enabled=true` 全局启用；Caffeine 异步加载、Token Bucket 限流的 sleep 均运行在虚拟线程上，避免阻塞平台线程。
- **动态配置**：核心限流参数（Semaphore permits、Token Bucket QPS）通过 Nacos `@RefreshScope` 热更新，无需重启。
- **背压管理**：`VirtualThreadBackPressureManager` 监控每个 Consumer Group 的 in-flight 消息数，触及高水位（100,000）时暂停消费者，恢复到低水位（50,000）后自动恢复。

## 二、 核心项目亮点 (Project Highlights)

### 亮点 1：两层解耦的责任链 Pipeline 设计

**设计背景：** 消息从 API 接收到最终投递需要经历多个独立的处理阶段（校验、组装、去重、屏蔽、投递），这些阶段之间高度独立，但又需要有序执行。

**实现方式：**  
定义 `BusinessProcess<T extends ProcessModel>` 接口作为节点契约，`ProcessTemplate<T>` 持有有序节点列表，`ProcessController` 负责遍历执行；每个节点通过 `ProcessContext.setNeedBreak(true)` 短路后续处理。  
API 层 Pipeline（`PipelineConfig`）注册 4 个节点：`SendPreCheckAction → SendAssembleAction → SendAfterCheckAction → SendMqAction`。  
Handler 层 Pipeline（`TaskPipelineConfig`）注册 5 个节点：`DiscardAction → ShieldAction → DeduplicationAction → SensWordsAction → SendMessageAction`。

**工程价值：**  
- 单一职责，每个节点独立测试；
- 开闭原则，新增"黑名单过滤"只需实现接口并插入节点列表，**零侵入**；
- 节点可按渠道类型配置不同的 Pipeline 组合，支持精细化差异化处理。

---

### 亮点 2：Semaphore 背压 + Token Bucket 双层限流防雪崩

**设计背景：** 上游业务流量突增时，若不加控制直接透传到第三方渠道 API，会触发第三方限流或自身 OOM，引发雪崩。

**实现方式：**

- **第一层（MQ 入队背压）**：`MqRateLimiter` 持有 1,000 许可的 `Semaphore`，`SendMqAction.process()` 调用 `tryAcquire()` 失败则直接返回限流响应，保护 Kafka 生产者不被瞬时流量击穿。参数通过 Nacos `@RefreshScope` 动态调整。
- **第二层（渠道级限流）**：`TokenBucketRateLimiter` 按配置 QPS 分配令牌，超出则 sleep 等待。sleep 运行在**虚拟线程**中，不阻塞平台线程。`FlowControlFactory` 根据渠道类型路由到对应限流器，支持运行时更新 QPS。
- **第三层（消费端背压）**：`VirtualThreadBackPressureManager` 用 `AtomicLong` 追踪 in-flight 消息数，触及高水位 100,000 时调用 `container.pause()` 暂停 Kafka 消费，降至低水位 50,000 后自动 `container.resume()`，用 CAS 防止重复触发。

**工程价值：** 三层防护从入口到渠道全程保护，任意一层触发都不会压垮下游，系统在第三方限速情况下仍能优雅降级。

---

### 亮点 3：Prometheus + Grafana + Loki 端到端可观测体系

**设计背景：** 异步消息系统的问题往往难以复现，需要完善的可观测性才能快速定位。

**Metrics 层（Prometheus + Grafana）：**
- `ApiMetricsFilter` 自定义 `austin.api.request.duration` Histogram，配置 50ms/100ms/200ms/500ms/1s SLO 桶，开箱即得 P50/P95/P99 分位延迟；
- `KafkaMetricsBinder` 每 30s 刷新 `austin.kafka.consumer.lag` Gauge，快速发现消息积压；
- `PendingMetricsBinder` 暴露 `austin.mq.semaphore.permits` Gauge，实时反映入队限流水位；
- `BackPressureMetricsBinder` 暴露消费端 in-flight 水位，配合 Grafana 告警规则实现自动触发。

**Logging 层（Loki + MDC 全链路 traceId）：**
- `MdcEnrichFilter`（`HIGHEST_PRECEDENCE`）在 HTTP 入口注入 `traceId`（优先从 `X-Trace-Id` 请求头读取，否则生成 UUID），并写回响应头；
- `KafkaSendMqServiceImpl` 将 MDC 中的 `traceId` 写入 Kafka 消息头；
- `MdcInterceptor`（`RecordInterceptor`）在消费端从消息头还原 `traceId` 到 MDC，`afterRecord()` 清理；
- Logstash Encoder（`logstash-logback-encoder 8.1`）将所有日志格式化为 JSON，Promtail 采集后推送 Loki；
- Grafana 中一个 `traceId` 可串联从 HTTP 入口到第三方 API 调用的全部日志。

**工程价值：** 从"看不见"到"全透明"，线上告警触发后可在 5 分钟内定位根因。

## 三、 项目难点与解决方案 (Difficulties & Solutions)

### 难点 1：高并发下 Kafka 消息积压与下游第三方接口限流的冲突

**问题描述：**  
业务高峰期上游 HTTP 请求量可达 3,000+ QPS，Kafka 队列快速堆积消息；而下游短信/邮件服务商通常有严格的 QPS 限制（如某短信服务商单账号 500 QPS）。消费端若不加控制地全速消费，会频繁触发服务商限流（HTTP 429），导致大量消息发送失败；若用线程 sleep 等待限流窗口，又会导致线程资源耗尽。

**解决方案：**

1. **入队层 Semaphore 背压**：`MqRateLimiter` 持有 1,000 许可，Kafka 生产前调用 `tryAcquire()`，失败直接返回 `RATE_LIMIT` 响应，拒绝入队而不是阻塞，保持系统整体吞吐可控。
2. **渠道级 Token Bucket 限流（消费侧）**：`TokenBucketRateLimiter` 按渠道配置最大 QPS（如短信渠道 500 QPS），当令牌不足时计算需 sleep 的毫秒数并在**虚拟线程**中执行 `Thread.sleep()`，不占用平台线程，支持大量并发等待而无线程池压力。
3. **消费端背压（防 OOM）**：`VirtualThreadBackPressureManager` 在 in-flight 消息数触及高水位 100,000 时暂停 Kafka 消费者，等待处理完成后自动恢复，防止内存溢出。
4. **动态参数调整**：所有限流参数（Semaphore permits、Token Bucket QPS）通过 Nacos 动态下发，可在不重启服务的情况下根据下游限速策略实时调整。

**效果：** 在第三方渠道限速情况下，系统不再出现消息雪崩式失败，消息最终投递成功率保持在 **99.2%** 以上。

---

### 难点 2：异步链路下异常被吞没、排查困难

**问题描述：**  
消息推送是一个跨线程、跨进程的异步系统：HTTP 请求在 Web 线程处理，Kafka 消费在消费线程，第三方 API 调用可能又在其他线程池中。传统日志缺少上下文关联，一旦出现消息丢失或发送失败，只能通过时间范围大海捞针。同时，虚拟线程引入后，MDC 默认不会跨线程传播，线程池中的异常如果没有统一处理也会被吞没。

**解决方案：**

1. **全链路 traceId 注入与传播**：
   - HTTP 入口：`MdcEnrichFilter` 注入 `traceId` 到 MDC，同时写入响应头，调用方可用响应头中的 `traceId` 直接去 Loki 查日志。
   - Kafka 生产：`KafkaSendMqServiceImpl` 将 `MDC.get("traceId")` 写入 Kafka 消息头。
   - Kafka 消费：`MdcInterceptor` 从消息头恢复 `traceId` 到 MDC，`afterRecord()` 统一清理，防止线程池复用时 MDC 污染。
   - 跨线程传播：`MdcUtil.wrap(MDC.getCopyOfContextMap(), runnable)` 封装异步任务，确保虚拟线程中也能访问 MDC 上下文。

2. **结构化 JSON 日志**：Logstash Encoder 将 MDC 所有字段（traceId、templateId、messageId、requestIp 等）序列化为 JSON 字段，Loki 可直接按字段精确过滤，无需正则匹配。

3. **关键节点日志埋点**：在 Pipeline 每个 Action 的 `process()` 方法入口和关键异常路径显式打 `INFO`/`WARN` 日志，结合 `traceId` 可还原完整处理路径。

4. **消费端统一异常处理**：Kafka `ErrorHandler` 捕获消费异常并记录包含 `traceId`、`partition`、`offset` 的告警日志，方便人工或自动化重试定位。

**效果：** 问题从出现到定位根因的平均时长由原来的 **30 分钟** 降低至 **5 分钟**以内。

## 四、 模拟面试高频 Q&A (Mock Interview)

---

### Q1：为什么选用 Kafka 而不是 RabbitMQ 或 RocketMQ？在这个项目里 Kafka 怎么保证消息不丢失？

**😈 面试官追问方向：** 你说 Kafka 吞吐高，那它在什么情况下会丢消息？你的配置能覆盖所有丢消息场景吗？

**🎓 候选人回答：**

**选型理由：**  
Kafka 的设计天然适合这个项目的三个核心需求：

1. **高吞吐**：Kafka 顺序写磁盘 + 零拷贝（sendfile），单 Broker 可撑数十万 QPS；消息推送业务高峰短促，需要攒批写入能力，Kafka 的 `batch-size=64KB` + `linger.ms=5` 配置可以将小消息攒批发送，吞吐提升明显。
2. **消费侧可重放**：消息推送如果下游渠道临时不可用，需要能回溯历史消息重发；Kafka 消息持久化到磁盘并支持按 offset 重放，这是 RabbitMQ 推模型难以做到的。
3. **Consumer Group 水平扩展**：不同渠道（SMS、Email、WeChat）各用独立 Consumer Group，互不影响，扩容只需增加消费者实例，符合平台的渠道隔离设计。

RabbitMQ 推模型在高吞吐下消费者容易过载，路由灵活但不适合大规模攒批；RocketMQ 国内生态好，延迟队列内置支持，但团队技术栈更熟悉 Kafka，且项目 Flink 流处理层也使用 Kafka 数据源，统一技术栈降低维护成本。

**Kafka 消息不丢失保障（三端分析）：**

| 层级 | 风险点 | 配置/措施 |
|------|--------|-----------|
| **生产端** | 消息发送失败未感知 | `acks=all`：等待所有 ISR 副本写入才返回成功 |
| **生产端** | Broker 崩溃后重试导致重复 | `enable.idempotence=true`：开启幂等，Broker 去重同一 Producer 的重复消息 |
| **生产端** | 网络抖动 | `retries=3`：最多重试 3 次；`max.in.flight.requests.per.connection=5` 与幂等结合保证顺序 |
| **Broker 端** | Leader 宕机，Follower 数据未同步 | `acks=all` + 设置 `min.insync.replicas=2`，确保至少 2 副本同步后才确认 |
| **消费端** | 消费成功但 offset 提交失败（自动提交） | 现阶段用 `enable-auto-commit=true` + `auto-commit-interval=1000ms`，存在 at-least-once 语义；消费逻辑中 `DeduplicationAction` 通过 Redis 做幂等去重，确保重复消费不重复发送 |

**被追问"自动提交会丢消息怎么办"：**  
> "自动提交在消费成功前提交 offset 有丢消息风险，但在这个项目里 Handler Pipeline 是同步执行的，消费者线程处理完整个 Pipeline 才进入下一条消息，实际上自动提交时消息已经处理完毕。如果要更严格保证，可以改为手动提交（`enable-auto-commit=false`），在 `SendMessageAction` 第三方 API 返回成功后再调用 `consumer.commitSync()`，但代价是吞吐降低，需要权衡。"

### Q2：你的系统中使用了本地缓存（Caffeine）和 Redis，讲讲在配置拉取场景下，你们是怎么保证缓存一致性的？

**😈 面试官追问方向：** Caffeine 里有旧数据、Redis 里是新数据，用户发消息用的是哪份数据？如果 Redis 也是旧数据怎么办？

**🎓 候选人回答：**

**两级缓存架构：**

```
请求 → Caffeine L1（本机内存，最大 5,000 条，TTL 10 分钟）
         命中 → 直接返回
         未命中 → Redis L2（TTL 30 分钟）
                   命中 → 填充 Caffeine → 返回
                   未命中 → DB 查询 → 填充 Redis → 填充 Caffeine → 返回
```

**缓存一致性策略（强调以下三点）：**

1. **TTL 兜底（最终一致）**：Caffeine 10 分钟 TTL，即使数据变更，最多 10 分钟后本地缓存自动失效并从 DB 重建，满足消息模板偶尔更新的业务需求。对于消息推送场景，模板内容的轻微延迟（10分钟内）通常可接受。

2. **主动失效（配置变更触发）**：当运营人员在管理后台修改消息模板时，`MessageTemplateController` 的更新/停用接口在写 DB 成功后，同步调用 `messageTemplateCaching.invalidate(templateId)` 清除 Caffeine 缓存（若用集群则需广播失效）。Redis 使用 `del` 命令主动删除对应 Key，下次请求时从 DB 重新加载。

3. **缓存穿透防护**：对于 DB 中不存在的 `templateId`，Caffeine 缓存哨兵对象 `NULL_MESSAGE_TEMPLATE`，TTL 同样 10 分钟，避免每次 miss 都打到 DB，防止恶意请求或逻辑 bug 导致的穿透。

**被追问"集群多实例下 Caffeine 各自不一致怎么解决"：**  
> "是的，这是 Caffeine 作为进程内缓存的天然缺陷。在单机部署阶段主要依赖 TTL 兜底。如果要解决集群一致性，有两个方向：一是把消息模板变更事件发布到 Redis Pub/Sub 或者 Kafka，各实例订阅后主动 invalidate 本地 Caffeine；二是缩短 L1 TTL（比如 1 分钟），用稍高的 DB 压力换取更强的一致性。目前业务对模板数据的一致性要求不是强实时的，10 分钟 TTL + 主动失效的方案已经满足需求。"

### Q3：看到你接入了 Prometheus 和 Loki，如果 Grafana 报警显示接口 P99 延迟突然飙高，你会按照什么思路去排查？

**😈 面试官追问方向：** P99 飙高你怎么判断是应用问题还是 Kafka 消息积压？Loki 日志怎么查？你说的每一步要怎么操作？

**🎓 候选人回答：**

**排查思路（分层下钻，先定位层级，再找根因）：**

**第一步：确认影响范围（1 分钟）**

```
Grafana → austin.api.request.duration_p99 折线图
  - 对比各 path（/api/send、/api/recall）的 P99 趋势
  - 确认是全接口飙高（系统级）还是单接口飙高（业务级）
  - 对比 QPS 指标：如果 QPS 未涨但 P99 飙高，说明是处理变慢而非流量突增
```

**第二步：检查 Kafka 消费积压（2 分钟）**

```
Grafana → austin.kafka.consumer.lag 指标
  - 如果 lag 突然升高，说明消费速度跟不上生产速度
  - 原因可能是：下游第三方 API 变慢、消费者线程池满、GC 停顿
  - 如果 lag 正常，说明瓶颈在 API 层，不在消费端
```

**第三步：检查限流水位（1 分钟）**

```
Grafana → austin.mq.semaphore.permits 指标
  - 如果剩余许可接近 0，说明入队被限流，大量请求在等待，导致 P99 升高
  - 解决：通过 Nacos 动态调高 permits 或扩容 Kafka 生产者

  → austin.backpressure.inflight 指标
  - 如果 in-flight 触及高水位，消费者被暂停，积压进一步加剧
```

**第四步：Loki 日志关联分析（3 分钟）**

```
Grafana Explore → Loki 数据源
  LogQL: {app="austin"} | json | duration > 500  # 过滤慢请求日志
  
  找到慢请求的 traceId，再执行：
  {app="austin"} | json | traceId="xxx-yyy-zzz"
  
  还原完整链路：
  - MdcEnrichFilter 打印的入口时间
  - SendPreCheckAction / SendAssembleAction 各节点耗时
  - SendMqAction 的 Kafka send 耗时（是否阻塞在 Semaphore.acquire()）
  - 消费端 DeduplicationAction Redis 耗时
  - SendMessageAction 第三方 API 响应时间
```

**第五步：系统资源排查（2 分钟）**

```
JVM: Grafana → jvm.gc.pause duration
  - 如果有 Full GC 停顿，是 JVM 问题，考虑调整堆大小或优化内存使用

线程: jvm.threads.live 是否异常增长（虚拟线程理论上不限，但 carrier 线程池满会挂载虚拟线程）

外部依赖: Redis 响应延迟（redis.latency）、DB 慢查询日志
```

**定位总结话术：**  
> "P99 飙高我会沿着数据流从入口到出口逐层排查：先看 lag 确认是不是消费侧；再看 semaphore permits 确认是不是被限流；然后用 Loki 拿到 traceId 还原慢请求的完整链路，定位到具体哪个节点耗时异常；最后结合 JVM metrics 和外部依赖指标确认是否是资源问题。整个流程在指标完备的情况下，5 分钟内可以定位到具体代码行。"

### Q4：讲一下你项目里发消息的责任链模式（Pipeline）是怎么设计的？如果我现在要临时加一个"黑名单过滤"节点，需要怎么改代码？

**😈 面试官追问方向：** 如果某个节点抛出未检查异常会怎样？节点顺序怎么保证？你说零侵入，那 ProcessTemplate 里的列表不还是要改吗？

**🎓 候选人回答：**

**责任链框架设计（4 个核心类）：**

```java
// 1. 节点接口 - 定义每个处理节点的契约
public interface BusinessProcess<T extends ProcessModel> {
    void process(ProcessContext<T> context);
}

// 2. 处理上下文 - 携带数据和流控标志
public class ProcessContext<T extends ProcessModel> {
    private Integer code;          // Pipeline 标识
    private T processModel;        // 业务数据（如 SendTaskModel）
    private Boolean needBreak;     // true = 终止后续节点
    private Object response;       // 节点间传递的响应对象
}

// 3. 流程模板 - 持有有序节点列表
public class ProcessTemplate<T extends ProcessModel> {
    private List<BusinessProcess<T>> processList;  // 有序节点列表
}

// 4. 流程控制器 - 遍历执行
public class ProcessController {
    private Map<Integer, ProcessTemplate> templateMap;  // code → template

    public void process(ProcessContext context) {
        ProcessTemplate template = templateMap.get(context.getCode());
        List<BusinessProcess> processList = template.getProcessList();
        for (BusinessProcess process : processList) {
            process.process(context);
            if (Boolean.TRUE.equals(context.getNeedBreak())) {
                break;  // 短路
            }
        }
    }
}
```

**Handler 层 Pipeline 配置（`TaskPipelineConfig`）：**

```java
@Bean("smsTaskTemplate")
public ProcessTemplate<TaskModel> smsTaskTemplate() {
    ProcessTemplate<TaskModel> template = new ProcessTemplate<>();
    template.setProcessList(List.of(
        discardAction,
        shieldAction,
        deduplicationAction,
        sensWordsAction,
        sendMessageAction
    ));
    return template;
}
```

**新增"黑名单过滤"节点的步骤（3步，5分钟内完成）：**

```java
// Step 1: 实现 BusinessProcess 接口
@Component
public class BlacklistAction implements BusinessProcess<TaskModel> {
    @Autowired
    private BlacklistService blacklistService;

    @Override
    public void process(ProcessContext<TaskModel> context) {
        TaskModel taskModel = context.getProcessModel();
        List<String> receivers = taskModel.getTaskInfo().getReceiver();
        
        // 过滤黑名单用户
        List<String> filtered = receivers.stream()
            .filter(r -> !blacklistService.isBlacklisted(r))
            .collect(Collectors.toList());
        
        if (filtered.isEmpty()) {
            context.setNeedBreak(true);  // 全部是黑名单，终止 Pipeline
            context.setResponse(SmsResponse.failed("ALL_BLACKLISTED"));
            return;
        }
        taskModel.getTaskInfo().setReceiver(filtered);
    }
}

// Step 2: 注入到 TaskPipelineConfig 的节点列表
// 在 discardAction 之后，shieldAction 之前插入 blacklistAction
template.setProcessList(List.of(
    discardAction,
    blacklistAction,   // ← 新增一行
    shieldAction,
    deduplicationAction,
    sensWordsAction,
    sendMessageAction
));

// Step 3: 完成。原有节点代码零改动。
```

**被追问"ProcessTemplate 里的列表不还是要改"：**  
> "是的，`ProcessTemplate` 的节点列表本质是有序的 Bean 集合，新增节点需要在配置类里加一行。这里'零侵入'的含义是**原有节点代码不变**——`ShieldAction`、`DeduplicationAction` 等已有节点的 `process()` 方法完全不需要修改，只有 Pipeline 组装配置类（类似 `wiring` 层）需要加一行声明。这符合开闭原则：对扩展开放（加新节点），对修改关闭（旧节点代码不动）。如果要彻底不改配置，可以给 `BusinessProcess` 加 `@Order` 注解并让框架自动扫描注册，但当前项目显式配置更直观，可读性更好。"

**被追问"节点抛出未检查异常怎么处理"：**  
> "目前 `ProcessController` 没有对节点异常做 try-catch，节点抛出的运行时异常会向上传播，由 Spring 的全局异常处理器（`@RestControllerAdvice`）捕获并返回统一错误响应，同时 MDC 中的 `traceId` 确保异常日志可被追踪。对于消费端的 Kafka 消费异常，由 Kafka 的 `ErrorHandler` 兜底，记录 partition + offset + traceId 便于人工重试。如果要更细粒度的节点级熔断，可以在 `ProcessController` 的循环里加 try-catch，对特定异常类型设置 `needBreak` 而不是抛出，这是一个可以演进的优化点。"

### Q5：你如何设计幂等，防止消息重复发送给用户？Kafka 重平衡或者重试时会不会出现重复通知？

**😈 面试官追问方向：** 你说幂等，幂等 Key 怎么设计？模板变量不同但业务 ID 相同怎么办？

**🎓 候选人回答：**

我把幂等拆成了**平台幂等**和**业务幂等**两层：

1. **平台幂等（默认）**：在 `DeduplicationAction` 里基于模板 ID、接收人、内容指纹、时间窗口生成幂等 Key，落 Redis（Set 或 String + TTL）。消费端即使重复拉到同一条消息，也会在幂等层被挡住，保证“最多一次触达”。
2. **业务幂等（可选增强）**：允许业务方透传 `bizId`（如订单 ID）。若 `bizId + channel + receiver` 已发送成功，则直接返回重复提交，避免业务重试导致用户重复收到通知。

**幂等 Key 设计原则：**

- 要包含足够业务语义：`dedup:{templateId}:{receiver}:{contentHash}:{timeWindow}`
- 要有 TTL：比如短信 24h、营销消息 1h，避免 key 无限制增长
- 要支持策略化：验证码类（强幂等，短窗口）、营销类（弱幂等，长窗口）

**被追问"模板变量变化怎么办"：**
> "如果变量变化导致内容变化，`contentHash` 也会变化，这类消息应视作新消息；如果希望按业务主键去重，就切到 `bizId` 语义幂等。我的做法是把幂等策略做成模板配置项，由运营按模板类型选择。"

### Q6：第三方短信服务商出现高失败率（比如 5xx）时，你如何做降级和故障切换？

**😈 面试官追问方向：** 你是怎么判定服务商故障的？切换后如何避免抖动？

**🎓 候选人回答：**

我会用**熔断 + 多供应商路由 + 恢复探测**三件套：

1. **故障判定**：按供应商维度统计 1 分钟窗口失败率、超时率、P99。比如失败率 > 20% 且连续 3 个窗口，触发熔断。
2. **路由切换**：`SendMessageAction` 调用渠道 Handler 前先查路由策略，主通道熔断则切到备通道（如 SupplierA -> SupplierB）。
3. **避免抖动**：熔断后设置最短打开时间（如 60 秒），期间只放行少量探测流量（5%）做半开恢复，探测通过再全量切回。

**数据一致性处理：**

- 切换期间 `messageId` 不变，回执按同一业务键聚合，避免报表重复统计
- 失败消息写入重试队列，避免在主链路做阻塞重试

### Q7：你在项目里用了虚拟线程。那它和线程池有什么边界？什么时候不适合虚拟线程？

**😈 面试官追问方向：** 虚拟线程会不会把数据库连接池打满？会不会有锁竞争问题？

**🎓 候选人回答：**

虚拟线程解决的是“线程数量”问题，不直接解决“下游资源容量”问题。

- **适合场景**：I/O 等待多、任务生命周期短（比如调用第三方 API、异步缓存加载）
- **不适合场景**：长时间持有重量级锁、CPU 密集计算、受限资源特别小（如 DB 连接池 50）

**我在项目里的边界控制：**

1. 虚拟线程主要用于 Caffeine 异步加载、限流等待 sleep、批处理并发，不用于无限制打 DB。
2. 所有外部资源仍用显式限流（Semaphore/Token Bucket）保护，防止\"虚拟线程很多\"把 Redis/DB/第三方接口打挂。
3. 对可能 pinning 的代码（同步块 + 阻塞调用）做审查，尽量避免在 synchronized 临界区里做远程调用。

**一句话总结：**
> “虚拟线程让并发更轻，但容量治理仍要靠限流、连接池和背压。”

### Q8：如果 Kafka 出现 Rebalance 抖动，消费延迟明显升高，你会怎么处理？

**😈 面试官追问方向：** 你会调哪些参数？如何减少 Rebalance 期间的不可用时间？

**🎓 候选人回答：**

我会从“减少无效 Rebalance”和“缩短 Rebalance 时间”两方面处理：

1. **减少无效 Rebalance**
   - 消费实例优雅下线（preStop + drain）
   - 调整 `session.timeout.ms`、`heartbeat.interval.ms`，避免短时抖动被误判下线
   - 业务线程不要长时间阻塞 poll 线程，避免触发 max poll 相关超时
2. **缩短 Rebalance 时间**
   - 分区数与实例数合理匹配，避免超大 Group
   - 尽量让单条消息处理时长稳定（慢调用异步化或转重试队列）
3. **可观测性**
   - 监控 `consumer lag`、`rebalance count`、`poll interval`，出现抖动时快速定位到实例或分区

**项目落地话术：**
> “我们通过背压把慢处理从主消费线程中剥离，Rebalance 期间 lag 上升幅度控制在可接受范围，恢复后 1-2 分钟内回到稳态。”

### Q9：如果要保证“发送任务可追踪、可审计、可重放”，你会如何设计消息状态机？

**😈 面试官追问方向：** 状态很多会不会导致写放大？如何避免并发更新状态错乱？

**🎓 候选人回答：**

我会定义明确状态机并做单向流转：

`INIT -> MQ_SENT -> CONSUMED -> CHANNEL_REQUESTED -> SUCCESS/FAILED -> RETRYING -> DEAD_LETTER`

**设计要点：**

1. **事件驱动落库**：只在关键状态边界写库，普通日志进 Loki，避免每一步都写数据库。
2. **幂等更新**：`update ... where status = oldStatus`（CAS 语义）防止并发覆盖。
3. **可重放**：失败消息带上 `messageId + lastStatus + retryCount` 写入重试/死信 Topic，可按条件回放。
4. **可审计**：审计视图按 `messageId` 聚合状态迁移时间线，便于追责和复盘。

### Q10：你如何做安全与合规？比如短信/邮件内容里有敏感信息时如何处理？

### Q11：你怎么做容量评估和压测？为什么说这个项目能抗 3500 QPS？

### 1. 虚拟量化数据口径（必须背熟，防追问）

| **高峰期 Kafka Lag** | < 500 条 | 正常消费速度 3,000+ 条/s，Lag 不超过 0.5s 积压量 |
| **Caffeine 缓存命中率** | ~98% | 5,000 模板容量，热门模板常驻，TTL 10 分钟，日常变更频率低 |
| **Semaphore 许可数** | 1,000 | 经压测调优，1,000 许可下系统 CPU 利用率约 70%，留有扩容余量 |
| **Token Bucket 短信渠道 QPS** | 500 QPS | 对应短信服务商单账号限制，超出自动等待（虚拟线程中 sleep） |

### 2. 全局架构数据流转话术

**面试官问："当一个发短信的 HTTP 请求打进来，到最终用户收到短信，中间经过了哪些组件？"**

**标准回答（30 秒版本）：**

> "HTTP 请求首先经过 `MdcEnrichFilter` 注入 `traceId`，然后进入 API 层的 4 节点 Pipeline：参数校验、模板组装（这里会查 Caffeine L1 缓存）、账号验证（查 ChannelAccountCaching），最后 `SendMqAction` 调用 `Semaphore.tryAcquire()` 做背压判断，通过后用 Kafka Producer 写入 `austinBusiness` Topic，`acks=all` 确保写入成功。
>
> Kafka 消费端，短信 Consumer Group 拉取消息，`MdcInterceptor` 从消息头恢复 `traceId`，然后进入 5 节点 Handler Pipeline：丢弃检查、夜间屏蔽、Redis 去重、敏感词过滤，最后 `SendMessageAction` 根据渠道类型路由到 `SmsHandler`，`SmsHandler` 用 Token Bucket 做渠道级限流后调用阿里云短信 SDK 发出 HTTP 请求，最终用户收到短信。整个链路通过 `traceId` 可在 Loki 全程追踪。"

**全链路组件清单（可详细展开）：**

```
HTTP 客户端
    ↓ POST /api/send
Nginx（反向代理）
    ↓
Spring Boot Web（MdcEnrichFilter → ApiMetricsFilter → Controller）
    ↓ Pipeline [PreCheck → Assemble → AfterCheck → MqAction]
    ↓ Semaphore.tryAcquire()（1,000 许可背压）
Kafka Producer（acks=all, idempotent, snappy, batch=64KB）
    ↓ Topic: austinBusiness（8 分区，3 副本）
Kafka Broker（ZooKeeper/KRaft 协调）
    ↓
Kafka Consumer（SMS Consumer Group，MdcInterceptor 恢复 traceId）
    ↓ Pipeline [Discard → Shield → Dedup → SensWords → Send]
    ↓ Redis（去重 SISMEMBER）
    ↓ Token Bucket（500 QPS 渠道限流，虚拟线程 sleep）
SmsHandler（调用阿里云短信 SDK）
    ↓ HTTPS
阿里云短信网关
    ↓ 运营商通道
用户手机收到短信 ✅

旁路链路：
- Prometheus 每 15s 采集 /actuator/prometheus
- Grafana 实时展示 P99 延迟、Kafka Lag、Semaphore 水位
- Logstash Encoder → Promtail → Loki（JSON 日志 + traceId 字段）
- XXL-Job 定时触发：刷新 GeTui Token、处理夜间延迟消息（NightShieldLazyPendingHandler）
- Flink 消费 austinTraceLog Topic 做实时数据分析（送达率、渠道成功率）
```

### 3. 超纲防御：未来的优化与演进方向

**面试官问："你觉得这个项目还有什么不足，或者你会怎么继续优化它？"**

**方向 1：引入延时消息队列，实现第三方限流时的智能退避重试**

> "目前消息发送失败（如第三方返回 429）的处理是 Token Bucket 等待，属于同步阻塞式重试，占用消费线程资源。更优雅的方案是：引入 **RocketMQ 延时队列** 或自研 **Redis ZSet 延时队列**（`zadd key {timestamp+retry_delay} {messageId}`），将失败消息写入延时队列，消费端定时扫描到期消息重新投递，实现指数退避（1s → 5s → 30s → 5min），彻底解耦重试逻辑与消费主流程，也更容易实现死信队列兜底和告警。
>
> 具体实现：Cron 定时任务通过 `ZRANGEBYSCORE key 0 {now}` 扫出到期消息，反序列化后重新投入 Kafka `austinBusiness` Topic，同时更新重试次数；超过最大重试次数（如 5 次）的消息打入死信 Topic 并发告警。"

**方向 2：基于 Redis HyperLogLog 实现全局去重防打扰（按日/周维度）**

> "现有的 `DeduplicationAction` 基于 Redis Set 存储消息内容 Hash，在用户量大时 Set 的内存占用会线性增长，且 Key 的设计是按消息内容去重，不能满足'同一用户 24 小时内同类型消息最多发 N 条'的频次控制需求。
>
> 优化方向：使用 **Redis HyperLogLog** 实现大基数用户的近似去重（误差 0.8%，内存固定 12KB/Key），用于全局维度统计；对于精确频次控制，用 **Redis INCRBY + EXPIREAT** 实现滑动窗口计数器（Key: `dedup:{userId}:{channel}:{dayOfYear}`，TTL 1 天），每次发送前先 INCR 判断是否超限，超限则丢弃并记录日志。这样可以在不影响主流程性能的前提下实现完整的用户维度防打扰策略。"

**方向 3：引入 Outbox + CDC，彻底收敛“写库成功但 MQ 发送失败”的一致性风险**

> "当前是先走业务处理再投 Kafka，理论上仍有少量'业务落地成功但 MQ 发送失败'窗口。可引入 Outbox 模式：业务事务内把待发送事件写入 outbox 表，再由 CDC（Debezium）订阅 binlog 异步投递 Kafka。这样消息投递和业务提交共享一个本地事务边界，可靠性更强。"

**方向 4：分层优先级队列 + 配额系统，保障核心通知不被营销消息挤压**

> "把消息按 P0/P1/P2 分优先级，Kafka Topic 或分区上做优先级隔离；消费端结合租户配额（QPS/quota）调度。突发流量时优先保障验证码、风控类消息，营销类自动降速或延后，避免关键业务 SLA 被拖垮。"

**方向 5：多机房容灾与同城双活，提升可用性到 99.99%**

> "现阶段是单地域主备，可演进为同城双活：Kafka Mirror 同步、Redis 主动-主动或主从热备、配置中心多活。入口通过 GSLB 做就近接入，单机房故障时 30 秒内完成流量切换。"

**方向 6：模板智能路由与 A/B 实验平台，提升触达效果**

> "在发送链路中引入实验分流（比如 80/20），同一消息在不同文案/发送时机上做 A/B 测试。结合点击率、转化率、退订率自动收敛最优模板，实现从'稳定发送'到'效果优化'的能力升级。"

**方向 7：统一回执中心与闭环报表，打通“发出-送达-点击-转化”全链路**

> "不同渠道回执格式不统一，建议建设回执标准化中心，把短信/邮件/IM 回执统一映射到标准事件模型，再写入实时数仓。业务侧能按模板、渠道、地域、运营活动做漏斗分析，直接指导投放策略。"

**方向 8：策略引擎化（规则 DSL），把“写代码改规则”升级为“运营可配置”**

> "将黑名单、频控、夜间屏蔽、内容校验抽象成规则 DSL（如 JSON Rule / Aviator），由规则引擎执行。运营可在后台热更新规则并灰度发布，研发只维护引擎与安全沙箱，大幅缩短策略上线周期。"

**方向 9：成本治理与弹性伸缩，按业务峰谷自动扩缩容**

> "把单位消息成本（Kafka、Redis、第三方通道费用）纳入指标体系，结合 HPA/KEDA 按 lag、QPS、RT 自动扩缩容。在大促峰值自动扩容、夜间低谷自动缩容，兼顾 SLA 与资源成本。"

**方向 10：AI 辅助异常诊断与自动化处置**

> "结合 Loki 日志和 Prometheus 指标做异常模式识别：自动聚类出'第三方超时型'、'缓存击穿型'、'分区热点型'故障，并触发 Runbook 自动化操作（限流收紧、切备通道、触发重试队列），将 MTTR 从分钟级进一步压缩到秒级响应。"
