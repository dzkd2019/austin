# Austin 高并发消息平台 — 压测场景与 SLA 目标设计

> **Manager**：方案直接输出，不废话。三个场景，每个场景给出通过标准（Pass Criteria）。

---

## 场景一：基准测试（Baseline Test）

### 目标
在单机预热完成后，确立系统在正常水位下的性能基准，验证 JVM JIT 编译、本地缓存命中率、虚拟线程调度稳定性均已达到稳态。

### 执行参数

| 参数              | 值                               |
|-----------------|----------------------------------|
| 并发虚拟用户数（VUs）    | 100                              |
| 持续时间            | 5 分钟（前 2 分钟视为预热，后 3 分钟取样）       |
| 目标接口            | `POST /send`                     |
| 数据集             | `data/payloads.json`（1000 条随机数据） |

### SLA 通过标准（Pass Criteria）

| 指标                    | 阈值                    |
|-----------------------|-----------------------|
| P99 响应时间             | ≤ 200 ms              |
| P95 响应时间             | ≤ 100 ms              |
| 平均响应时间              | ≤ 50 ms               |
| 错误率（HTTP 非 200/202）  | ≤ 0.1 %               |
| 吞吐量（RPS）             | ≥ 500 req/s           |
| Kafka Producer 发送成功率 | ≥ 99.9 %              |
| JVM Heap 使用率         | 稳态不超过 70%，无 FGC 发生    |

## 场景二：突发流量测试（Spike Test）

### 目标
模拟瞬间 10 倍流量打入（从 100 VUs 瞬跳至 1000 VUs），验证系统的**背压（Backpressure）机制**和**限流策略**是否正确生效：超出阈值的请求应被拒绝并返回 429/503，而不是无限排队导致服务雪崩。

### 执行参数

| 参数              | 值                                 |
|-----------------|-----------------------------------|
| 流量模型            | 0→100 VUs（1 min）→ **1000 VUs（瞬跳）**（2 min）→ 100 VUs（1 min）|
| 目标接口            | `POST /send`                      |
| 数据集             | `data/payloads.json`              |

### SLA 通过标准（Pass Criteria）

| 指标                       | 阈值                            |
|--------------------------|-------------------------------|
| 服务不宕机                    | **必须**：进程在整个测试期间持续存活           |
| 限流触发时的响应码               | 429 或 503（不允许出现 5xx 超时挂死）      |
| 被限流请求的响应时间              | ≤ 50 ms（拒绝应快速返回，不能排队等待超时）      |
| 正常请求（未被限流）的 P99 响应时间   | ≤ 500 ms                      |
| Kafka Consumer Lag 峰值   | 峰值后 5 分钟内可自动消化恢复至 < 1000 条     |
| JVM Heap 在 Spike 期间     | 不触发连续 FGC（单次 FGC 允许 ≤ 1 次）    |
| 错误率（非预期 5xx 错误）        | ≤ 1 %                         |

## 场景三：疲劳测试（Soak Test）

### 目标
在 70% 正常负载（约 350 VUs）下持续运行 **2 小时**，暴露内存泄漏、数据库连接未释放、Kafka offset 积压、线程数缓慢增长等长时间运行才会显现的问题。

### 执行参数

| 参数              | 值                              |
|-----------------|-------------------------------|
| 并发虚拟用户数（VUs）    | 350（线性爬坡至 5 分钟，随后持续 115 分钟）   |
| 持续时间            | 120 分钟                         |
| 目标接口            | `POST /send`                   |
| 数据集             | `data/payloads.json`           |

### SLA 通过标准（Pass Criteria）

| 指标                          | 阈值                                          |
|-----------------------------|---------------------------------------------|
| P99 响应时间漂移                  | 测试结束时 P99 与起始基准相比涨幅 ≤ 20%                   |
| 错误率                         | 全程 ≤ 0.5 %                                  |
| JVM Heap（Old Gen）趋势         | 不应持续单向增长；每次 FGC 后应可回落至稳定基线                  |
| JVM FGC 频率                  | 每小时 ≤ 2 次，单次 STW ≤ 1 s                      |
| Kafka Consumer Lag           | 全程 ≤ 5000 条，且无断崖式持续堆积（斜率超过 500 条/min 告警）    |
| 数据库连接池 Active 连接数           | 不超过连接池 max-size 的 80%，Wait 队列长度 全程为 0        |
| JVM 线程数                     | 平台线程（Carrier Thread）数量不持续增长，稳定在初始值 ±10% 以内  |
| 进程 RSS 内存                   | 全程增长幅度 ≤ 20%（相对测试开始时），不出现持续单调递增            |
